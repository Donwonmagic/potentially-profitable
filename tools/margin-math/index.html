How we protect the numbers you type

Nine claims. Each one is verifiable in your own browser in under a minute. If any of them turn out to be wrong, we want you to find out first — open every "Inspect this" and check us.

1

Your numbers never leave this page.

No fetch(), XMLHttpRequest, or form submission fires when you type a financial number. The calculator math runs entirely in your browser.

Inspect this
Open DevTools (Cmd+Opt+I / Ctrl+Shift+I) → Network tab. Type a number into the calculator above. The request list should not grow. If it does, that's a bug — tell us.
2

There's no server to store them on.

The only endpoint this page uses is GET /tools/margin-math/. No /api/margin-math-save, no /api/calculate, no logger. The Worker can't hear you.

Inspect this
From a terminal: curl -X POST https://muntin.digital/tools/margin-math/. Response: 405 Method Not Allowed (or similar) — there's nothing listening for POSTs.
3

Analytics sees only buckets, never numbers.

Plausible receives properties from a short, fixed list of enumerated values. A \$25 ticket becomes 25-39. A 30% food cost becomes 28-32. Your raw numbers are never a value on any event.

Inspect this
DevTools → Network → filter plausible. Interact with the calculator. When the event fires, look at its payload. Values like ticket_bucket: "25-39" — never ticket: 25.00.
4

No cookies, no localStorage, no sessionStorage — for your inputs.

Your typed numbers live only in JavaScript variables, which disappear when you close the tab. There's no persistent state for the calculator.

Inspect this
DevTools → Application → Storage. Use the calculator. Check Cookies, Local Storage, Session Storage, IndexedDB for this origin — the panels stay empty of any financial value.
5

No third-party scripts touch the inputs.

This page loads exactly two JavaScript files: site-wide site.js (nav + language switch) and tool-specific margin-math.js (the math). Plus one analytics script (Plausible) that receives the bucket values. Glossary hover popovers read their definitions from data-def attributes in the HTML itself — no additional fetch fires when you hover.

Inspect this
DevTools → Network → filter JS. Reload. You should see plausible.io/js/…, site.js, and margin-math.js. Hover any underlined glossary term in a calculator — the request list does not grow. No Google Tag Manager, no Meta Pixel, no chat widget, no session replay.
6

Shareable scenario links keep numbers out of the server logs.

Your inputs live in the URL fragment — the part after the #. Per HTTP specification, browsers never send fragments to servers. Click Copy scenario link on any calculator: the link you paste is an audit trail you control — nothing leaves your browser when you move a slider, and nothing leaves ours when you share the link.

Inspect this
Move any slider and watch the URL bar. It updates to something like …/margin-math/#v=1&dbe.t=25&dbe.f=30&pc.f=32&pc.l=34. That fragment is never in an HTTP request. We also set <meta name="referrer" content="no-referrer"> on this page so outbound clicks can't leak it to a third party via the Referer header.
7

The source is readable.

No build step, no minification, no framework. The math module is plain JavaScript — you can read every line.

Inspect this
Right-click this page → View Page Source. Or open /tools/margin-math/margin-math.js directly. Search for function mmCalcDeliveryBreakeven — that's the whole math, in the open.
8

Nothing persists beyond this tab.

Close the tab, reopen the tool: every calculator resets to default. There's no account, no saved history, no "welcome back."

Inspect this
Change every slider and input. Close the tab. Reopen /tools/margin-math/. Everything is back to its starting value.
9

The Monthly Report and calendar reminder are 100% client-side.

"Print this month's report" opens your browser's native print dialog — we never see the output. "Add a monthly check-in" generates an .ics file in your browser and downloads it locally. The calendar event includes only the URL fragment shown in your address bar.

Inspect this
DevTools → Network. Click Print this month's report — no new requests. Click Add monthly check-in — still no new requests; a margin-math-monthly.ics download appears. Open it with a text editor: every field in the event is a plain-text copy of values already visible to you.

How to check if any tool is safe

Five tests you can run on any free financial tool you encounter — before you type a single real number into it. We score ourselves alongside a typical lead-generation free tool so the difference is concrete, not rhetorical.

The test Margin Math Typical free tool
1. Does typing a number trigger a network request?Open DevTools → Network. Type. No requests fire. Every keystroke POSTs to a server.
2. Is the privacy claim at the point of input?Not buried in a policy page. "Stays in your browser" badge on every card, full 8-step panel in-page. Privacy Policy link in footer only; implicit consent on submit.
3. Is there an account / newsletter / cookie gate?Anything demanding "accept all" before you can use the tool. Nothing — no gate, no popup, no cookie banner. "Enter your email to see your results."
4. Any third-party analytics, session replay, marketing scripts?DevTools → Network → filter JS. Privacy-first Plausible only; bucket props (never raw values). Google Analytics, Meta Pixel, HubSpot, session replay — stacked.
5. Is the source code readable?Right-click → View Source. Unminified, under ~500 lines, every math function named. Minified SaaS bundle; math hidden inside a framework dashboard.

Apply the same five tests to any calculator, estimator, or "free audit" you encounter — especially one asking for revenue, margin, food cost, or labor numbers. A tool that silently POSTs your inputs is storing them. A tool with no in-page privacy claim is dodging the question. You're allowed to walk away.

What to share, where

Four tiers of your business data

Not every number belongs in every conversation. Most small-business owners carry all their data in the same mental bucket — which means the supplier list and the tax ID get the same protection (often the same low level of it). Four tiers, each with a different audience and a different level of caution.

Tier 1

Public

Everything anyone can find on your site, your listing, or a walk-by.

  • Menu, hours, photos
  • Address, phone, website URL
  • Schema.org markup, cuisine tags, service attributes

Share with: Anyone. Optimize aggressively — this is how customers find you.

Tier 2

Competitive-sensitive

Legal to share, but useful to a rival — or leverage for a platform.

  • Cost of goods, supplier list, negotiated pricing
  • Commission tier you actually pay (not the public rate)
  • Labor schedule template, daypart mix, menu-engineering matrix

Share with: Bookkeeper, consultant, broker — under NDA. Not platforms, not competitors, not "free audit" tools that keep your input.

Tier 3

Operational-confidential

Your actual operating numbers, customer pipeline, employee details.

  • Monthly P&L, actual food cost %, actual margins
  • Reservations pipeline, customer database, loyalty data
  • Employee names, schedules, tipped-employee distributions

Share with: Inside the business only. POS vendor, payroll processor, accountant — and only under a written contract that specifies what they can and can't do with it.

Tier 4

Regulated

Legally protected. Losing this has fines, lawsuits, or criminal exposure attached.

  • SSN, EIN, other tax identifiers
  • Customer card data (PCI scope), employee bank details
  • Food-safety logs, health-department correspondence, liquor-license status, I-9s

Handle with: Encrypted storage, access logging, contracts with cybersecurity terms. Never email. Never in a shared spreadsheet. If a vendor asks for this casually, that alone is a flag.

Apply this anywhere you're asked to hand data over — vendor evaluations, contracts, loan applications, "free audit" intakes. The pattern: data never flows up a tier. A Tier 3 vendor doesn't get Tier 4 access just because they asked. A Tier 1 audience (a platform, a listing site, a competitor) doesn't get Tier 2. The easiest way to reduce your attack surface is to stop volunteering data that wasn't actually required.
