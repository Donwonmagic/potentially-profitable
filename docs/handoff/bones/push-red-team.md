# The Red Team — how this plan fails in execution

## Thesis
The plan does not fail in month three; it has already failed, and the failure is invisible because the instrument that would report it is the thing that broke. `node scripts/check-queue.mjs` exits 2 in every one of its eight modes — including `--self-test`, the mode built to catch this — because one item, Q-004, carries `status: "closed"`, a string not in the schema's enum (scripts/check-queue.mjs:96, validated at :238). Q-004 is the only item closed since the plan was written, and it was closed by hand by "orchestrator", bypassing `--done`, in an invented `closure` field while the schema's real `closed` field stayed null, recording not that the work was done but that the finding was REFUTED — a state the schema has no name for. The mechanism's very first contact with reality produced a bypass, and the bypass disabled the mechanism. Then `.claude/hooks/session-start.sh:49` swallows the error (`--brief 2>/dev/null || true`), so a session today receives eight paragraphs of CORE rules, zero queue items, and two permanent NOTEs about broken bookkeeping — I ran the hook and confirmed it. An honest agent that obeys SF-QUEUE-FIRST runs the gate, gets a schema error and no work list, and does what every agent session at Muntin has always done: invents work. From there the cascade is arithmetic. Q-014 — one of four items in `whatIsNeverDropped` — verifies `scripts/check-cost-index-snapshot-freshness.mjs`; the file on disk is `check-cost-index-snapshot-fresh.mjs`, so `--done` refuses to close it forever, and Q-014 blocks Q-001 → Q-020/21/22/24 → Q-017 → Q-030 → Q-031 → Q-041 → Q-042, an eight-deep serial chain containing both day-90 deliverables. The founder's week-3 attention does not go to Q-002 (asking his employer for written permission to upload their vendor prices to his own company — the single irreversible, socially expensive, deadline-free item on which everything else depends); it goes to the red deploy, because that is the only feedback loop this company has ever responded to, and check-all takes minutes to run and returns 319-320 of 328. And when nothing lands, no falsifier fires: every one of the nine kill criteria presupposes a receipt file that non-execution never produces, so the historically most likely outcome — a 26% close rate — is the one outcome the plan is structurally unable to detect, leaving a past-due checkpoint whose verdict must be recorded by the same person whose non-delivery is the subject, with `amend` on the menu.

## Findings
- **The plan's central instrument is dead in all eight modes, and the mode that would have caught it is disabled by the same fault. `node scripts/check-queue.mjs` with no args, `--brief`, `--budget`, `--checkpoints`, `--render`, `--self-test`, `--verify`, `--next` and `--absorb` all exit 2 with `Q-004: status must be one of ready|claimed|blocked|done`. The validator (scripts/check-queue.mjs:238) runs before mode dispatch (:1152), so `--self-test` cannot execute and `--render` cannot self-heal QUEUE.md.** — On day 1 of execution the plan has no readable work list. Every downstream mechanism — claiming, closing, the budget, the checkpoints, one-in-one-out — routes through this one binary. This is not a bug that degrades the plan; it is the plan's off switch, already flipped.
- **Q-004 is how it broke, and how it broke is the whole story. data/queue.json Q-004 was closed 2026-08-07 by `by: "orchestrator"` via a hand-written `closure` object that is not in the schema, with the schema's real `closed` field still null and `status` hand-typed to the illegal string "closed". It was closed as REFUTED, not done. Its `closure.note` names the actual defect — "The defect was the orchestration (no worktree isolation), not check-all" — and `grep -c worktree data/queue.json` returns 1: that note itself. No queue item exists for worktree isolation.** — Within hours of building a mechanism whose one novel claim is that closure is machine-proved, the first closure was written around the machine, in an invalid state, disputing rather than doing — and the act disabled the machine for every subsequent session. The concurrency defect it diagnosed and declined to queue (six agents in one tree) is also the most plausible cause of the malformed field. The failure mode is self-reproducing.
- **All ten checkpoint verify commands are broken shell, not broken work. Every `mustBeTrue[].verify.cmd` embeds `const need=["Q-002", "Q-014", "Q-001"]` inside a double-quoted `node -e "..."`. I executed one: `ReferenceError: Q is not defined`. Separately, they test `ix[id].closed`, a property that only two items carry, while the schema tracks completion via `status: 'done'`.** — Every checkpoint fails for a quoting bug indistinguishable from failing for work-not-done. CP-30 on 2026-09-06 will report the same thing whether the founder delivered everything or nothing. A falsifier that cannot distinguish success from failure is not a falsifier.
- **A typo permanently blocks the undroppable spine. Q-014 (`whatIsNeverDropped`, capacity.floorPlan) verifies `node scripts/check-cost-index-snapshot-freshness.mjs` in the product repo. The file on disk is `/home/user/Muntin-Invoice-Decoder/scripts/check-cost-index-snapshot-fresh.mjs`. `--done` runs verify and refuses to close on failure, so Q-014 can never close. Q-014 blocks Q-001, which blocks Q-020/Q-021/Q-022/Q-024 → Q-017 → Q-030 → Q-031 → Q-041 → Q-042. Five other items name scripts that do not exist: Q-025 (check-limits-register.mjs), Q-030 (check-specimen-close.mjs), Q-032 (check-pack-check-tool.mjs), Q-033 (build-refusals-page.mjs, build-freshness-page.mjs).** — Doing the work correctly cannot close the item, and the item gates both day-90 deliverables. Worse: nobody will discover this, because the gate that would run the verify does not run at all. The founder does 15 minutes of real work, the machine says no, and the machine's credibility — the only thing distinguishing this from the 26% audits — is spent on a spelling error.
- **The plan measured that only 10% of founder hours get paid, then budgeted 100% of nominal capacity. `data/queue.json:1447` records `realizedRate.value: 0.1` (~3 of 31 maintenance-hours-due paid in 30 days). It appears in the RENDER (scripts/check-queue.mjs:429) and nowhere in `budget()` (:177-202), which divides declared hours by the nominal 13h floor. M1 sums to 14.5h + 2.5h overhead = 17h against a 13h floor = 131%, and `budget()` returns verdict `over-floor` — a warning (:197). Only >26h fails. No receipt anywhere records founder hours actually spent.** — The single most predictive number in the plan is rendered as prose beside a budget that ignores it. The floor the plan claims to be sized against cannot fail the budget, so the one gate on capacity can only fire on a month nobody was ever going to attempt. And with no hours-delivered receipt, no checkpoint can distinguish 'the strategy was falsified' from 'August was busy at Tacombi' — while two of the kill criteria END THE STRATEGY.
- **No kill criterion fires on non-execution. All nine `killIf` tests presuppose a receipt file that only completed work produces: CP-30 reads `founder-walk.json#dollarSurvivalPct`, CP-60 reads reviewer verdicts and `deskMinutesPerClose`, both CP-90 criteria presuppose ≥8 recorded conversations. `checkpointPolicy.whoRecords` = founder, and `amend` is an available result guarded only by the prose sentence 'or it is a kill being called a proceed'.** — The plan is falsifiable against every outcome except the one its own history predicts. A 26% close rate produces no verdict, only a checkpoint the founder must adjudicate about his own non-delivery, with a graceful exit available. This is the exact shape of the four prior plans.
- **`deskMinutesPerClose` — the input to 2 of 6 CP-60/CP-90 kill criteria and, per the plan's own text, the number the cohort ceiling turns on — appears in exactly five files, all storefront planning prose (queue.json, QUEUE.md, ADR-030, ADR-032, ADR-033). Zero occurrences anywhere in /home/user/Muntin-Invoice-Decoder. Relatedly, `closeStatement` / `statementUrl` appear nowhere in apps/web or apps/api, while Q-042's doneWhen requires a signed close with a `statementUrl`. There is no `/close/` directory in the storefront and no close route in the product.** — The artifact being sold has no producer and the measurement deciding the business's ceiling has no source. Two kill criteria can never evaluate, and the day-90 deliverable requires a URL for a document nothing renders. The plan sells a dated statement of food cost and contains no item that builds one.
- **The hook — the plan's answer to '1 of 108 transcripts carried a CLAUDE.md' — currently delivers zero work and two permanent complaints. I ran `.claude/hooks/session-start.sh`: it prints eight CORE rules, then nothing from the queue (line 49 pipes the failure to /dev/null), then `NOTE: docs/handoff/QUEUE.md has been hand-edited` (unfixable — `--render` exits 2) and `NOTE: the working set is over budget` (fails by construction until Q-080). QUEUE.md already disagrees with queue.json: it lists Q-002 as '1h + a conversation'; queue.json says `founderHours: 2`.** — Silence is indistinguishable from 'no open work', and two NOTEs that print every session forever become invisible by week two. The hook was built precisely because rules that load 1% of the time are not rules — but a hook that reliably reports nothing is worse than no hook, because it certifies that the pointing happened.
- **The two ratchets that hold are ratchets, not forcing functions. `check-honesty-debt.mjs` exits 0 with 10 of 14 items OWED (including HD-13, the red deploy). `check-src-sentinel.mjs` exits 0 at UNANCHORED=138 DRIFT=21 because `data/src-sentinel-budget.json` is set to today's values. `audit-gate-teeth.mjs` measures 132 gates: 8 HAS-TEETH, 24 NO-TEETH, 3 ALREADY-RED, and 96 NO-JSON-INPUT — unmeasurable — while HD-14's doneWhen only requires the NO-TEETH list to be cleared. Meanwhile check-queue.mjs is not in `scripts/check-all.mjs` at all.** — The only forcing function this company has ever had is 'a red gate blocks the Cloudflare deploy'. The queue, the checkpoints and the honesty debt are all outside it. They record intent with excellent hygiene and compel nothing — which is the definition of the 26% mechanism, rebuilt in JSON.
- **There is no acquisition surface for 60 of the 90 days, and the item that creates one is the lowest-priority item touching revenue. Four `waitlist` forms exist (index.html, ledger/index.html and both ES mirrors) and no `/close/` anywhere. Q-040 — '/close/apply/ replaces all four waitlist forms' — is LOW, M3, blocked on Q-010 and Q-030, 0.5 founder-hours. Q-041 requires eight qualified conversations and no item in the plan produces a single name.** — The board called 'no acquisition mechanism for the first ten customers' disqualifying. The plan's answer is a LOW-priority M3 page behind two blockers, and CP-90's falsifiers both presuppose the eight conversations already happened. The plan can therefore reach day 90 having disproved nothing, because the mechanism that would generate the evidence was never scheduled.
- **The plan's own decision-of-record citations are wrong in ways that prove the ADRs were not open while it was written. `capacity.ofRecord` cites `docs/editorial/decisions/ADR-030-the-ninety-days-and-its-falsifiers.md`; on disk ADR-030 is `one-price-one-cohort-no-billing-code.md` and the ninety-days ADR is ADR-033. Q-042's `why` justifies 'no SKU, no checkout, no billing code' as 'by ADR-027' — ADR-027 is the contract-loads-through-the-hook decision.** — Small on its own, but it is direct evidence about process: the capacity block that governs the entire plan names a file the author did not check. A future session resolving a dispute will follow the citation, find the wrong document, and re-litigate a decision that was already made — which the plan itself names as the other half of the 26% close rate.
- **Twenty-five of 46 items carry `founderHours: 0`, including all four correctness fixes (Q-020/21/22/24) that CP-60 turns on and that the price depends on. Founder review overhead is a flat 2.5h/month constant regardless of agent output volume, and Q-017 — 1.5h for the founder to deploy apps/api and apps/web to production — is his first deploy of services the plan's own engineering finding says have no working deploy path. `close-identity-eval.test.ts` carries 7 tests with 2 `it.todo` against four named defects.** — 'Pure agent work' is not free: it is founder review, founder merge, founder deploy, and founder judgment when an agent's fix is wrong. Pricing the four hardest engineering items at zero founder-hours is how M2 silently becomes the month everything stops, and the eval that would prove the fixes correct is itself unfinished.

## Proposals
- [~2 agent-hours, 0 founder-hours. Item (e) needs one founder decision — accepting that a missed checkpoint reds the deploy — which is the point.] **Repair and harden the instrument, make its failure LOUD, and put it inside the only forcing function that has ever worked. Concretely: (a) fix Q-004 — either write a real `--done` closure or add an explicit `refuted` status to STATUSES with a required `refutedBy` measurement, because 'the finding was wrong' is a legitimate and frequent outcome the schema currently forces people to lie about; (b) fix the six wrong script names (Q-014, Q-025, Q-030, Q-032, Q-033) and the ten checkpoint shell-quoting bugs; (c) rewrite `--self-test` to run against an in-file fixture so it can execute while production data is malformed; (d) change `.claude/hooks/session-start.sh:49` from `2>/dev/null || true` to printing the failure verbatim — a broken queue must be the loudest thing a session sees; (e) wire `node scripts/check-queue.mjs --checkpoints` into `scripts/check-all.mjs` so a past-due checkpoint with `result: null` blocks the Cloudflare deploy. Point (e) is the whole proposal; the rest is prerequisite. Nothing at Muntin has ever been closed because it was on a list, and everything that got closed was closed because a red blocked the deploy.** — This is the difference between a mechanism that changes the incentive and one that records the intent. Today the queue, the checkpoints and the honesty debt sit outside `check-all` and compel nothing — the queue is not even referenced in check-all.mjs. The honesty debt exits 0 with 10 items owed; src-sentinel exits 0 at UNANCHORED=138 because the budget was set to today's number. Ratchets prevent regression; only the deploy gate has ever produced payment. Until missing a checkpoint costs the founder the ability to ship, the plan's falsifiers are a wish with extra steps — and the current state, where the instrument is silently dead and the hook hides it, is strictly worse than having no queue, because it certifies that the pointing happened.
- [~2 founder-hours moved into M1 (fits the drop order by taking Q-001 at its 4h lower bound, which the floorPlan already contemplates). Re-parenting the four correctness items is a JSON edit.] **Break the eight-deep serial chain and fund the Q-002 'no' branch as a scheduled M1 item today. Q-002 (employer authorization) → Q-001 → Q-020/21/22/24 → Q-017 → Q-030 → Q-031 → Q-041 → Q-042 is fully serial, and its first link is the single most socially expensive, most deferrable item in the plan: asking his employer, in writing, for permission to upload their vendor identities and negotiated prices into a service he controls and intends to sell from. CP-30 already names the fallback — 'the walk and the specimen move to a consenting third restaurant or to reconstructed data' — but there is no queue item for it, no founder-hours, no name, and no date. Create it now, in M1, with hours: identify and ask one consenting non-employer restaurant, in parallel with Q-002, not after it fails. Separately, un-block Q-020/Q-021/Q-022/Q-024 from Q-001: those four defects were diagnosed from code reading and committed fixtures, not from a founder walk, and holding the correctness work hostage to a conversation with a GM is what turns a slipped conversation into a lost quarter.** — Every deliverable in the plan currently depends on one conversation that has no deadline, real career risk, and a plausible answer of 'let me check with our counsel' that consumes three weeks. When it slips — and the item most likely to slip in a 13h/month plan is the one requiring courage rather than time — the plan has no parallel track, and CP-30's designed fallback is an unfunded instruction. Parallelising the evidence base costs a few hours and removes the plan's single point of failure. Un-blocking the correctness fixes converts M2 from 'everything waits on the founder' into 'agents work while the founder negotiates'.
- [~1.5 agent-hours for the schema, the receipt and the budget change. The hours receipt costs the founder about a minute per session, and is the cheapest instrument in the plan.] **Make non-execution a measured, machine-decided outcome, and make the budget read the number it already knows. Add `docs/handoff/receipts/hours.json` — founder hours actually spent per window, recorded as work happens — and add to every checkpoint a fourth `killIf` with `decidedBy: measurement` that fires on DELIVERY rather than results: e.g. 'fewer than N of this window's mustBeTrue items closed via --done' → `result: stall`, which cannot be amended without naming the item that replaced the terms. Then change `budget()` (scripts/check-queue.mjs:177-202) to read `capacity.realizedRate` — which the file already carries at 0.1 and currently only renders as prose at line 429 — and fail, not warn, when declared hours exceed the floor. Also delete `deskMinutesPerClose` from all six kill criteria or add the item that instruments it; a criterion whose input exists in zero lines of code in either repo is decoration, and two of six currently are.** — Every one of the nine kill criteria presupposes a receipt that only completed work produces, so the plan is falsifiable against every outcome except the one this company's history predicts. Right now, if nothing is done, CP-30 arrives with founder-walk.json absent, no killIf can evaluate, and the founder — the person whose non-delivery is the subject — records the verdict with `amend` on the menu. That is the four prior plans, exactly. A stall verdict the machine issues, plus a budget that respects the 10% realized rate the plan already measured and then ignored, is what converts 'we built a queue this time' from an assertion into a structural difference. It also protects the founder honestly: it lets the plan say 'this was not attempted' instead of forcing a false choice between 'falsified' and 'proceed'.
