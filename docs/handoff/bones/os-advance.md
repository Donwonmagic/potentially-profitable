# Advancing the Field — what these frameworks do not solve

## Thesis
Muntin's real gap is not that it lacks enforcement; it is that its enforcement has never been evaluated, and no framework in the source material evaluates a deterministic gate corpus. I ran five real mutations against the live repo today and the result is worse than the audit's hand-classification predicted: I aged a tool's "Last verified" stamp to 2020-01-01 and `check-tool-verified-stamp.mjs` printed "14 tool page(s) clean"; I inverted the meaning of a published security claim ("never"→"always", "We do not"→"We do") and `check-security-claims.mjs` printed "all rendered + schema'd"; 96 files carry a fabricated JSON-LD persona and `check-fabrications.mjs` — the file CLAUDE.md calls "the absolute fact gate" — prints "0 blocklist hits". One of five mutants was cleanly killed. That is a measurable, publishable number the field does not currently compute, and it is my first contribution: mutation-score the evaluators, not the code. My second is sharper and more general: every published number sits in exactly one of three states — TRANSCLUDED (re-injected by a builder), FROZEN (citing an immutable address), or UNBOUND (hand-typed, citing a mutable path) — and Muntin's 2,228 transcluded numbers across 617 files have produced zero recorded falsehoods while its 165 unbound annotations, all in one file, produced ~72; the remedy is not a re-checking gate but a publish-time address minter, and `cost-index/week-2026-07-06.json` already holds the exact immutable address (`#basket.pct` = -0.0496) that the flagship post should have cited. My third contribution is forced by this engagement's own failure: the audit cites `check-counts-coherence.mjs:72` as proof the count sentinels are enforced, when line 72 is `SENTINEL_STRIP` — the line that deliberately exempts them — and a fifteen-agent adversarial layer confirmed it, because it was shown the maker's citation instead of being made to open the file. Decoy-calibrated verification fixes that at a cost of one extra proposition per batch. I am explicitly not recommending the wiki-compile pattern, cost-per-accepted-change, worktree-per-worker, or a different-model-family judge, because each costs founder-hours it cannot repay here or reads healthy while the company decays.

## Design
### C1 — Gate mutation harness: `scripts/check-gate-mutation.mjs` + `data/gate-mutants.json` [1 agent session for the harness plus 20 seed mutants (the five in this report are already written and reproduced). ~2 founder-hours/quarter to add mutants when a new gate lands. Runtime: mutants are per-gate, not per-suite, so nightly cost is seconds, not the 186s of check-all.]
A registry of `{gate, subject, edit, expect: "kill"|"survive", why}` rows. The harness copies the repo to a scratch tree, applies each edit, runs the named gate, records kill/survive to `data/gate-mutation-score.json`, and writes a per-gate score. A gate with score 0 and no dated waiver fails the harness. Seed with the 20 mutants covering the gates the audit hand-classified SHAPE, starting with the five I already ran (aged verified-stamp, inverted security claim, fabricated persona, altered count sentinel, deleted figcaption). Runs nightly, opens/updates a single rolling Issue on score regression, reusing `flake-tracker.yml`'s existing diff-and-issue shape. The harness has read-only access to `scripts/` — it may not edit the gates it scores.

- Naive: Point mutmut (already running nightly at `mutmut-nightly.yml`) at more application code, and/or write more paired unit tests in the shape of `scripts/test-article-graphics.mjs`.
- Evolved: Neither reaches the risk. `services/extract` is deterministic Python already covered by a determinism gate; the unexamined epistemic system is the 169-gate corpus, and 3 of 129 storefront gates have any test at all — all three pinning parser helpers on synthetic strings, which cannot detect that `check-security-claims.mjs` will pass a page whose claims have been inverted. Mutating the REAL corpus is the only test that answers "would this gate have caught the thing it is named for." Read-only access to `scripts/` is the write-permission split from the factory pattern applied where it actually buys honesty: a harness that could edit a gate to make its own score go up is worthless.

### C2 — `scripts/check-number-binding.mjs`: the three-state classifier [1 agent session. The classifier is ~120 lines; `data/frozen-sources.json` is the design work and is ~10 patterns.]
Walk every reader-facing HTML page. Classify each published numeral: inside `<!-- count: -->` or `<!-- repro: -->` = TRANSCLUDED; carrying `<!-- src: -->` whose path matches an entry in a new `data/frozen-sources.json` (patterns: `cost-index/week-*.json`, `data/cost-index-editions.json#editions[asOf=…]`) = FROZEN; carrying `<!-- src: -->` naming a mutable file or a runtime object (`dispatch.*`, `data/cost-lockfloat.json`) = UNBOUND → fail. Report the three counts on every run so the ratio is visible in the log.

- Naive: The audit's own NOW action: `check-src-annotations.mjs` re-derives the live value behind each annotation and compares it to the number in the prose.
- Evolved: Re-deriving fails here in two ways. Mechanically: 6 of the 45 annotated lines name `dispatch.*`, which is not a file key at all — it exists only as a runtime object inside `build-cost-index-dispatch.mjs`, so the gate would have to reproduce the dispatch pipeline and would be as fragile as the thing it checks. Semantically it is worse: a dated of-record edition is SUPPOSED to be permanently true, so a gate that reds whenever the market moves converts a one-time defect into a standing monthly correction obligation — precisely the class of work with a measured 0% close rate outside the originating session. Classifying the BINDING is O(1) per annotation, cannot false-positive on a data refresh, and its remedy is a one-time address rewrite that retires the obligation instead of creating one.

### C3 — `scripts/stamp-edition-citations.mjs`: the publish-time address minter [1 agent session including the backfill of all 45 lines and the two seed snapshots. Thereafter it is a build step in the dispatch chain, zero founder-hours.]
At publish, for each `<!-- src: dispatch.X -->` in `blog/cost-index-*/index.html`, resolve X against the edition's frozen snapshot and rewrite in place to `<!-- src: cost-index/week-<asOf>.json#X -->`. Three branches: (a) the frozen address exists → rewrite; (b) no frozen artifact exists for that source but it carries an `asOf` (e.g. `data/cost-lockfloat.json`, 14 commits, `asOf` present) → MINT one at `cost-index/lockfloat-<asOf>.json` and cite that; (c) the source is genuinely live with no as-of semantics → refuse to publish the number as a standing fact; it must be transcluded via a sentinel or relabeled with an inline date. Ship with `scripts/check-frozen-immutable.mjs` asserting that any path in `data/frozen-sources.json` has exactly one commit. Backfill the 45 annotated lines in `blog/cost-index-2026-07/index.html` and mint the two missing seed snapshots (2026-06-05, 2026-06-16).

- Naive: Hand-correct the ~72 false numbers in the flagship post, then repeat that sweep after each monthly edition.
- Evolved: Hand-correction is the exact work class with a 26% close rate and 0% when it outlives its session — the 2026-07-28 pass listed "four corrected numbers in blog/cost-index-2026-07" as not-optional and ten days later the drift had widened, not narrowed. Minting makes the numbers structurally incapable of rotting, so the obligation retires itself rather than recurring monthly. The precondition already holds and I verified it: `cost-index/week-2026-07-06.json` has one commit ever and `#basket.pct` = -0.049648946840521666 is exactly the value cited. Branch (c) is the honest limit the naive version hides — some sources have no as-of semantics, and for those the correct answer is that the number may not be published as a standing fact at all.

### C4 — `scripts/check-sunset.mjs` plus a scheduled demotion PR [1 agent session for the gate and the demoter workflow. Stamping 129 headers is a mechanical pass an agent does in the same session. Ongoing founder cost is a one-line renewal per artifact per 180 days.]
Every `scripts/check-*.mjs`, every waiver registry entry (MANUAL / UNWIRED / ALLOW / HISTORICAL_WAIVERS / DEDUP_ALLOW), and every published cadence promise carries `Sunset: YYYY-MM-DD` in its header. A clock gate reads them all. On expiry a scheduled workflow opens a PR that DEMOTES the artifact exactly one rung — fail → warn → UNWIRED-with-reason → deleted — one rung per expiry period, never more. Renewal is one line: bump the date, state why. Seed all 129 gates at last-substantive-commit + 180 days.

- Naive: The memory-engineering decay policy: schedule a periodic review that dedups, consolidates, and prunes the store, with a human deciding on contradictions.
- Evolved: A review is a founder-hour, and the measured payment rate on founder-hour obligations here is ~10% (3 of ~31 maintenance-hours-due paid in 30 days). The decay literature assumes a curator with capacity; Muntin has none, so any policy whose unit of action is a decision will not execute. Demotion inverts the default: keeping costs one line, removing costs nothing, and nothing is ever lost abruptly. The underlying claim is testable and I believe it is the real reason decay policies fail in low-capacity organizations — deletion is irreversible and therefore demands a decision; demotion is reversible and therefore demands none. The one retirement event in company history (`56900d7ab`, 2026-07-28) removed 6 gates only because `/course/` died; nobody has ever retired a gate on its own merits.

### C5 — `data/obligations.json` + `scripts/check-obligation-emitters.mjs` [1 agent session. The gate is ~80 lines; the registry is the actual work and needs one founder pass to confirm which promises are real.]
One row per standing promise the company has PUBLISHED, each with `{promise, interval, evidence_path, emitter}`. Seed rows: warrant canary (monthly, `docs/warrant-canary.md`), quarterly transparency, the monthly dispatch, the changelog, tool `last verified` stamps, the `llms.txt` cadence prose, the 24-hour bilingual reply SLA at `apps/web/lib/copy.ts:3185`, the phone-callback promise at `:3201`, and the three inconsistent security-response windows. The gate FAILS on any row whose `emitter` is null. It publishes two numbers on every run: silent-obligation ratio (rows with no emitter ÷ rows) and deferred-obligation rate (emitted due-events still open past their interval ÷ emitted).

- Naive: Adopt the factory's cost-per-accepted-change and the 50%-acceptance floor as the health metric for the agent workforce.
- Evolved: That metric measures at the change, and Muntin's failures are almost entirely omissions. Its acceptance rate is effectively ~100% (80–84% of commits Claude-authored and merged), so the metric would print green while the warrant canary goes 89 days unsigned and the transparency report goes 37 days past its own published date. Emitter coverage is the only number in this family computable BEFORE any work happens, and it is the precondition for a close rate to mean anything at all — you cannot have a close rate on events nothing emits. Order matters: build the emitter registry first, then measure clearance, never the reverse.

### C6 — `docs/method/adversary-protocol.md` + `scripts/build-verification-batch.mjs` [1 agent session for the protocol document and the batch builder. Marginal cost per audit is ~1 proposition per batch plus the re-run cost of voided batches.]
Three rules, enforced by the batch builder. (1) A verifier receives ONLY the falsifiable proposition and the subject file paths — never the maker's evidence, reasoning, severity, or citation line numbers. It must independently produce evidence, and a cheap comparator diffs its evidence against the maker's; divergence is surfaced to the founder, never auto-merged. (2) Every batch of N propositions carries one DECOY the orchestrator has already disproved with a recorded command; a verifier that confirms the decoy has its entire batch voided and re-run. (3) Findings a verifier ADDS are written to `claims-pending`, never to the verified set. Per-run false-confirmation rate accumulates in `data/verification-calibration.json`.

- Naive: Eval engineering's stated rule — a judge from a different model family that does not see the maker's chain of thought — implemented as "hand the finding and its evidence to a hostile reader and ask them to refute it."
- Evolved: That is exactly what this engagement did, and it yielded 1 refutation in 235 (0.43%) while an uncontaminated sampler reading ten headlines cold refuted two. The failure is demonstrable, not theoretical: the audit asserts the count-sentinel class is enforced and cites `check-counts-coherence.mjs:72`, but line 72 is `SENTINEL_STRIP` — the line that exempts sentinel values from the check — and I reproduced a 171→999 mutation the gate calls "clean". A verifier handed only the proposition and the filename would have had to open line 72. The decoy is the genuinely new part: hiding reasoning is a hope, but a decoy MEASURES whether a given run was discriminating, per batch, at a cost of one extra proposition. Rule (3) removes the incentive that broke this audit — 34.9% of findings carried verdict ADVERSARY, meaning the adversary was paid in discoveries, not in kills.

### C7 — `data/mechanism-register.json`: every mechanism ships with its own kill condition [30 minutes, but credible only if written first. Zero ongoing cost; it is read by C4's existing clock.]
One row per mechanism in this design: `{name, claim, kill_condition, measure, review_date}`. Examples, written before the code: C1 — "if after 90 days no gate scoring 0 is found sitting above a live undetected violation, delete the harness"; C2/C3 — "if a FROZEN citation is ever found to have rotted, the state model is wrong and must be revised, not patched"; C6 — "run ≥20 batches; if decoy-passing batches do not refute real propositions at a higher rate than decoy-failing ones, the decoy measures nothing — delete it"; C5 — "if silent-obligation ratio does not fall within 60 days, the registry is a document, not a mechanism." `check-sunset.mjs` (C4) reads this file like any other artifact.

- Naive: Ship the six mechanisms and record them on the strategic board as SHIPPED.
- Evolved: That is precisely the pattern this panel diagnosed: this company converts findings into machinery faster than into fixes, machinery has never been retired, and gates went 111 → 129 in 23 days. A panel that adds six mechanisms with no kill conditions is the seventh instance of the failure it is analyzing. Writing the falsifier BEFORE the code is also the only thing that makes these claims scientific rather than plausible — and it is the field advance this panel is least entitled to skip, since I am asking the founder to spend six sessions on unproven mechanisms.

## Advance
- **Gate mutation scoring — mutation-test the EVALUATORS, not the code. For each deterministic gate, maintain a registry of (real subject file, minimal edit that violates the gate's stated invariant, expected verdict); apply the edit to a copy of the real corpus, run the gate, record kill/survive. Publish a per-gate and per-suite mutation score. A gate whose mutation score is 0 is a green line that carries no information, and it can now be named as such with a number instead of an opinion. Demonstrated live today: 5 mutants, 1 clean kill, 1 kill only via a self-healing idempotence check, 3 survivals — including a published security claim whose meaning was inverted while `check-security-claims.mjs` printed "all rendered + schema'd".**
  - Gap: Eval engineering judges LLM OUTPUT. Mutation testing (already running here at `mutmut-nightly.yml`) targets APPLICATION CODE. The software factory gates CODE CHANGES. Nothing in the source material evaluates a corpus of deterministic assertions — yet that corpus is what an agent workforce actually steers by, and here it is 169 gates that no one has ever scored. Falsification: if, over 90 days, no gate with mutation score 0 turns out to sit above a live undetected violation, the metric is decorative and the harness should be deleted. Muntin can build it in one session and it already has one confirming data point — `check-fabrications.mjs` scores 0 on the persona mutant and sits above 96 live violations.
- **Publication tense: the three-state model for any number a system publishes from a live store. TRANSCLUDED — the number is a sentinel re-injected by a builder, permanently current. FROZEN — the number cites an immutable, single-commit address, permanently true as-of its date. UNBOUND — the number was typed by a human and cites a mutable path; this is the only dishonest state and it is the one nobody names. The remedy is not a gate that re-derives values (which makes a dated of-record artifact a moving target); it is a publish-time ADDRESS MINTER, with the hard rule that if the publish step cannot mint an immutable address for a source, that number may not be published as a standing fact.**
  - Gap: None of the source material addresses static artifacts citing mutable sources — the failure where every claim was true at publication and rotted underneath a standing page. Muntin's ratio is the natural experiment: 2,228 TRANSCLUDED numbers across 617 files with zero recorded falsehoods, versus 165 UNBOUND annotations in a single file that produced ~72. Falsification: if a FROZEN citation is ever found rotted, the state model is wrong — so ship `check-frozen-immutable.mjs` asserting single-commit history on every frozen path. Buildable and provable today: `cost-index/week-2026-07-06.json` has exactly one commit and `#basket.pct` = -0.0496 is the address the flagship post should have cited; `data/cost-lockfloat.json` has 14 commits and needs a minted snapshot.
- **Decoy-calibrated verification. Give the verifier only the falsifiable proposition and the subject paths — never the maker's evidence, reasoning, or severity — and seed every batch with one proposition the orchestrator has already disproved by command. A verifier that confirms the decoy has its whole batch voided and re-run. Separately, findings the verifier ADDS go to a pending queue as new unverified claims rather than counting as verification output. This yields a measured per-run false-confirmation rate for a multi-agent audit, which nothing in eval engineering currently provides.**
  - Gap: Eval engineering prescribes hiding the maker's reasoning and pinning the judge's version, but offers no way to know whether a particular judge run was actually discriminating — you get a verdict with no sensitivity estimate. Every practical multi-agent audit, including this one, passes the full report to the verifier: 1 of 235 refuted (0.43%) here, against 2 of 10 by an uncontaminated sampler. The contamination is demonstrable in the audit's own text — it cites `check-counts-coherence.mjs:72` as proof the sentinels are enforced when that line is `SENTINEL_STRIP`, which exempts them, and the adversarial layer confirmed it. Falsification: run ≥20 batches; if decoy-passing batches do not refute real propositions at a measurably higher rate than decoy-failing ones, the decoy measures nothing and should be removed. Marginal cost: one proposition per batch.
- **Silent-obligation ratio, and emitter-before-metric ordering. The answer to "what is the metric for work that never got proposed" is that there is no such metric until something emits a due event — so the primary number is not a close rate but a COVERAGE number: standing published promises that have no emitter, divided by standing published promises. Only once that ratio falls does a deferred-obligation rate (due-events still open past their promised interval ÷ due-events emitted) become meaningful. Both are computable before any work is done, which is what makes them usable by an organization whose defining problem is that work does not happen.**
  - Gap: The factory's cost-per-accepted-change measures at the change and is blind to omission; here it would read ~100% acceptance while the warrant canary sits 89 days unsigned against a monthly promise and no `check-*.mjs` in either repo greps the word "canary". Muntin's storefront has exactly one Issue-emitting workflow covering seven gates, so its silent-obligation ratio is near 1 — the failures are literally uncountable, not merely uncounted. Falsification: if the ratio falls and the deferred-obligation rate does not follow within 60 days, then emitters are not the constraint and the diagnosis is wrong. Buildable in one session; the registry, not the code, is the work.

## Rejected
- The Karpathy wiki pattern (raw documents are source; compile once, query the compiled layer forever). Muntin already compiled: `docs/handoff/strategic-council-board.md` is 1,488 lines, `board-archive.md` is 993, both immaculate and dated, and the measured close rate on their contents is 26% with zero closures ever produced by anyone working them. Compilation is the strongest muscle in this company and the bottleneck is downstream of it. A recompile produces a fifth compiled artifact and one more thing to maintain.
- Cost per accepted change, and the 50%-acceptance floor, as the health metric for the agent workforce. Acceptance here is effectively ~100% — 80–84% of commits in both repos are Claude-authored and merged — so the metric prints green while the canary goes 89 days unsigned, the transparency report goes 37 days past its own date, and 96 files publish a fabricated persona. A metric that reads healthy during this failure is worse than no metric. Use silent-obligation ratio and deferred-obligation rate instead.
- One worktree per worker, and the earned-autonomy ladder that only ever widens. Both are designed for teams with parallel review capacity; Muntin has one reviewer whose scarce resource is attention, not isolation. Adding worktrees adds coordination surface with no reviewer to absorb it. I keep exactly one piece of the factory pattern — the write-permission split — and only where it buys honesty (C1's harness may not edit the gates it scores).
- A judge from a different model family, pinned and version-logged, as standing practice. The principle is right and the free half of it (the judge does not see the maker's reasoning) is in C6. The paid half — a second vendor account, per-run cost, and a standing version-pin obligation — adds a recurring maintenance line to a company already carrying ~53 obligation-hours/month against 13–26 available. Reject until there is a paying customer.
- More application-code mutation testing. `mutmut-nightly.yml` already runs it over `services/extract` and opens labelled Issues, and per the brief no session has ever read that queue. The pattern is correct and the target is wrong — retarget it at the gate corpus (C1) rather than deepen it where a determinism gate already covers the ground.
- The five-stage memory pipeline (capture → consolidate → retrieve → reconcile → decay) as a build target. Four of the five stages are not Muntin's problem: capture is excellent, consolidation is excellent, and retrieval is solved by contract (CLAUDE.md instructs every fresh session to read the board first). Building retrieval infrastructure spends hours on the one stage that already works. Only DECAY transfers, and the transferable form is C4's automatic demotion, not a curator-run prune.
- The CLAUDE.md rewrite (under 200 lines, universal-applicability test, emphasis-marker rationing) as a standalone deliverable. The rules are correct and the file is 113 lines already. What I reject is shipping the rewrite WITHOUT the verification step from the same source — run a real session, then have a second session review the transcript rule by rule for what was followed, ignored, or followed inconsistently. Without that, a rewritten CLAUDE.md is one more unmeasured artifact and becomes finding #51; with it, the transcript review is itself a mutation test on the instruction corpus and belongs alongside C1.
- Building the graph before watching real traces — including any orchestration graph derived from this engagement. This audit's own trace shows a verifier layer that refuted 0.43% of what it read; a graph built on top of that signal would route work using a measurement instrument that has never been calibrated. C6 must land before any multi-agent flow is hardened into a graph.
