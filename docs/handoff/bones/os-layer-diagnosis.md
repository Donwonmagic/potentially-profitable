# Layer Diagnosis — which of harness, loop, or graph owns each failure

## Thesis
I classified all 118 critical/high findings by owning layer: 46 (39%) belong to NO architectural layer — they need a human to write a price, a retraction, a legal review, or a feature; 32 (27%) are HARNESS; 22 (19%) are GRAPH; 18 (15%) are LOOP. The decisive number is inside the GRAPH bucket: all 22 are build-plane or data-plane flow failures (a builder absent from `build.command`, an artifact rebuilt then reverted, a storefront enum that does not match a product enum) and **zero are agent-plane flow failures** — so building an agent orchestration graph would close none of the 118. Muntin has already proven it has orchestration in surplus: a 38-agent workflow produced 235 findings against a measured 26% absorption rate, which means more routing multiplies the input to a saturated queue. The harness is where the money is, and the harness gap is not tooling but *ignition*: `grep -rln "claude-code-action" .github` returns nothing in either repo, so no agent session has ever been started by anything except the founder typing, while decay runs 60 days out of 60 (346 commits across 24 distinct days; 266 of them on 8 days). The detection layer already works and produces nothing anyone can pick up — `mutmut-nightly`, `ocr-bench-nightly` and `flake-tracker` have each failed **30 consecutive scheduled runs** through this morning, and `list_issues` on the product repo returns `totalCount: 0` for OPEN *and* CLOSED, so 90 machine-detected failures have yielded zero artifacts. My recommendation is deliberately smaller than the source material implies: run exactly **three** recurring agent jobs with **zero conditional edges**, and make adding a fourth require retiring one. The single highest-leverage harness fix — a runnable local copy of the 84-step deploy order — already shipped this morning as `scripts/rebuild-all.mjs`; what is still missing is the thing that runs it on a clock.

## Design
### The layer card — a 13-row diagnostic table, imported not inlined [45 minutes, one session]
`docs/ops/layer-card.md`, referenced from CLAUDE.md by a single line: `@docs/ops/layer-card.md — read before proposing any new gate, workflow, or document.` Contents, verbatim: (1) A check exists but nothing runs it → GRAPH → add the edge, or delete the check. (2) A check runs but asserts a shape, not the fact → LOOP → make it read ground truth, or delete it. (3) A check cannot run — no key, no network, no browser, no DB → HARNESS → supply the environment or move it to a named human job with a date. (4) The deploy is red and only a human can clear it → GRAPH (missing edge) → `node scripts/rebuild-all.mjs --pre-only`, then add the builder to build.command. (5) A local red the deploy heals → HARNESS (environment mismatch) → run rebuild-all, do NOT edit the gate. (6) An artifact is rebuilt and then discarded → GRAPH (broken join) → fix the staging pattern, never the filename. (7) Two committed documents give opposite instructions → HARNESS (contradictory state) → surface both, a human deletes one; never auto-merge. (8) A published promise decayed while nobody looked → HARNESS (no trigger) → put it on the job roster or change the published cadence. (9) A cron has failed N nights running → HARNESS (no consumer) → auto-disable at 3, leave exactly one artifact. (10) A published number is no longer true → NONE first, LOOP second → correct the prose, and only then wire the gate. (11) Nobody can tell whether it worked in production → HARNESS (observability) → one server-side counter committed to the repo. (12) Fourteen days produced nothing → HARNESS (no scheduler) → the weekly session, not a new document. (13) The fix needs a price, a lawyer, or a retraction → NONE → decision queue; an agent may never close it.

- Naive: Add the diagnosis rules to CLAUDE.md so every session sees them.
- Evolved: Storefront CLAUDE.md is 113 lines and product CLAUDE.md is 213 — already over the 200-line guidance — and every line loads into every session. A 13-row diagnostic table fails the universal-applicability test: it is situational guidance for the one moment a session is about to add machinery. Behind an `@import` it costs one line of always-loaded context and is read exactly when it changes a decision. The rows are also written as *first fix*, not as *principle*, because a verdict that does not change the next edge is a report.

### Three recurring agent jobs. Exactly three. Zero conditional edges. [3–4 hours to build all three; then token spend plus ≤3 PRs/week of founder review]
Job 1 `deploy-green`, Saturdays after the 13:00 UTC refresh: run `node scripts/rebuild-all.mjs`, commit the output, open a PR. Job 2 `alarm-triage`, Saturdays: read the last 7 days of Actions run conclusions in both repos via the GitHub API, run the time-decay gates, append to ONE queue file, and auto-disable any workflow at 3 consecutive failures. Job 3 `decision-queue`, monthly: produce at most 5 items that require a founder decision, each carrying either the exact command to run or the exact sentence to approve. Implemented as `create_trigger` Routines in the founder's existing Claude Code Remote environment (already available — no new infrastructure) or as `claude-code-action` crons. Hard rule written into the layer card: **adding a fourth job requires retiring one.**

- Naive: Build an orchestration graph — nodes, conditional edges, parallel fan-out, joins, recovery paths, human approval gates.
- Evolved: Zero of 118 findings are agent-plane flow failures, so every edge in that graph would be speculative. Muntin has already run the large-graph experiment: 38 agents, ~5.8M tokens, 235 findings, and a measured 26% absorption. The binding constraint is one reviewer's attention, and conditional routing does not create attention — it creates more PRs competing for it. Three fixed jobs with no branching means the founder's mental model of the system is three sentences long, which is the only model that survives a two-week gap. The retire-to-add rule exists because the measured failure mode here is proliferation (gates 90 → 320 in 33 days, nothing ever retired), not insufficient routing.

### Split by write permission in exactly one place — blast radius, not task [1 hour (settings.json permission blocks + a deny list in each Routine prompt)]
`deploy-green` gets write access to `data/`, `cost-index/`, `es/cost-index/` and generated page roots only. It is denied `blog/`, `library/`, `docs/`, `.github/`, `wrangler.jsonc`, `src/worker.js`, and anything under `apps/api/src/routes/`. `alarm-triage` may write the queue file and may open a PR touching `.github/workflows/`, but may never push to it. `decision-queue` is read-only and cannot commit at all. Protected paths (CI config, auth, secrets, migrations, lockfiles, published legal pages, `sourced-claims.json`) always reach the founder as a diff, never as a merged change.

- Naive: Split agents by task — a maker, a reviewer that physically cannot edit what it reviews, a tester, an integrator.
- Evolved: The maker/reviewer split buys honest reports, and this company measurably does not act on reports: 26% close rate, zero closures ever produced by working a list. A second review agent would add token cost and one more document to a backlog that is already the product. What the split genuinely buys here is *containment*: 39% of findings are content, legal and pricing decisions where an autonomous edit is worse than no edit — the seven Spanish audio tracks speaking a retired $499 price, the perpetual price lock on 51 surfaces, the 72 live falsehoods. So keep exactly one instance of the pattern, aimed at blast radius, and drop the rest.

### Observability of the agent, built out of git rather than out of new infrastructure [2 hours (one script, four lines in CLAUDE.md's commit convention)]
Every agent commit carries structured trailers: `Layer: harness|loop|graph|none`, `Closes-finding: audit-2026-08-07#34`, `Evidence: <the exact command run, and its one-line output>`, `Session: <id>`. Then `scripts/close-rate.mjs` reads finding IDs out of `git log --format=%(trailers)` against the findings index and prints one number. The board header carries that number and nothing else about audits.

- Naive: Add tracing — a session-transcript store, per-run artifacts under `runs/`, a dashboard, or an LLM-judge that reviews transcripts rule-by-rule.
- Evolved: A `runs/` directory is a new artifact class in a repo that has never retired one and just added 307,721 lines of JSON in a day; it would be the fifth memory store and the fourth nobody queries. The trace already exists — 277 of 346 commits in 60 days are agent-authored, retained forever, free to store, and greppable with no tooling. The evolution that matters is making the *metric* free: measuring the 26% close rate cost an entire agent session of git archaeology, which is exactly why it had never been measured before and will not be measured again. With trailers it costs one second, which is the only condition under which the rule "no new multi-agent audit until close rate exceeds 50%" becomes enforceable rather than aspirational.

### An external heartbeat whose absence is the signal [30 minutes]
One scheduled push notification (or a one-line uptime check against `muntin.digital/cost-index/` and a committed timestamp), hosted *outside* both repos — the founder's Routines environment or a phone-level reminder. It fires weekly and asserts two things: the last storefront deploy succeeded, and `alarm-triage` ran. If the founder stops receiving it, that is the alarm.

- Naive: Add another cron in `.github/workflows/` that checks whether the other crons are healthy.
- Evolved: Finding 97 is the trap: GitHub silently disables scheduled workflows in a public repo after 60 days of inactivity, so a monitor hosted in the repo it monitors switches off under exactly the condition it exists to detect. And the empirical case is already on the board — `freshness-heartbeat` was built as the absence alarm and has run once, ever. The design property the source material never states is that **an alarm's own liveness must be observable from outside the system it monitors**. One notification the founder expects and stops receiving satisfies that; nothing inside `.github/` can.

### A decision queue, kept structurally separate from the work queue [1 hour to create; the discipline is the ongoing cost]
`docs/handoff/decisions-open.md` — hard-capped at 12 rows, each row: the decision, the two or three options, the one fact that would settle it, and a review date. Agents may APPEND and may never close a row. Job 3 refills it monthly from the findings index; the founder clears rows. The work queue (the thing `alarm-triage` writes) is a different file that agents both write and close.

- Naive: One prioritized backlog with severity labels — the audit's 235 findings ranked, worked top-down.
- Evolved: 39% of the 118 findings — the largest single bucket — cannot be closed by any agent under any architecture: a counsel review, a price, a retraction, an entity filing, "go run your own product once." Mixing them into one backlog is what produced the measured 26%: the founder opens a list, the first six items need him, and the list becomes shelf-ware. Separating them makes the work queue fully agent-closable (so its close rate can approach 100%) and makes the decision queue small enough to clear in one sitting. The cap of 12 is the forgetting policy applied before the store grows: a 13th decision requires deciding one.

### Retire the three permanently-red crons before adding any job [90 minutes for all three]
`mutmut-nightly`, `ocr-bench-nightly` and `flake-tracker` have each failed 30 consecutive scheduled runs. For each: read one run's log, then either fix it or delete the workflow. Then encode the rule — a scheduled job that fails 3 consecutive runs auto-disables itself and leaves exactly one artifact naming what it was watching and who turned it off.

- Naive: Wire the failing crons into the triage session so an agent starts working their output.
- Evolved: The naive move points a scheduled agent at a queue that does not exist — both repos have `totalCount: 0` issues, ever, because these jobs die before their `gh issue create` step. Worse, a cron that is red every night is indistinguishable from no cron and actively trains the founder to ignore Actions email, which is the same dynamic the audit measured on the deploy (37.5% phantom reds, PR #536 merged with three reds accepted). Auto-disable at 3 is the stopping rule the loop layer is missing: it converts a permanently-ignored signal into one dated artifact and an honest gap.

### Site observability: instrument the ~40 pages that can convert, not the 1,368 [2–3 hours; the CSV row is free once alarm-triage exists]
Analytics on the four waitlist forms, the five free tools, `/ledger/`, `/try/`, and the Cost Index hub plus the top ingredient pages — roughly 40 surfaces. One server-side counter in the Worker for signups by source, committed as a dated CSV row by `alarm-triage` each week so the number lives in the repo and survives a dashboard nobody opens.

- Naive: Add Plausible to all 1,368 pages and fix the three KPI tiles that query goals no code emits.
- Evolved: 79% of the site emitting no analytics is a real finding, but the denominator is wrong: instrumenting 1,368 pages produces a traffic report, and this founder's blocking question is not "which page gets read" but "did anyone raise their hand, and from where" — a question 40 pages answer and 1,328 do not. It is also the cheapest way to avoid repeating the KPI failure, where three of four tiles query goals no code path produces: build the counter first, then the tile, never the reverse. The weekly CSV row exists because a dashboard is a pull instrument and this company's measured pattern is that nothing gets pulled — the number has to arrive in the repo, next to the work.

## Advance
- **A mechanical decision procedure for the most common diagnosis, which the source material asserts is necessary but never supplies. For any check, gate, or gate-shaped promise that is not working: **exists but nothing runs it = GRAPH; runs but asserts the wrong thing = LOOP; cannot run because the environment lacks something = HARNESS.** Applied to Muntin this rule classified roughly 40 of the 118 findings without judgement calls.**
  - Gap: "Diagnose which layer owns a failure before changing architecture" is stated as a discipline with no procedure, so in practice the layer gets assigned by whichever framework the reader most recently read. A company with 169 gates needs the check-shaped case to be mechanical, because that is where its failures concentrate.
- **Naming the two planes the harness/loop/graph framing conflates. GRAPH means agent-plane flow (how sessions hand work to each other) OR artifact-plane flow (how builders, workflows and repos hand data to each other), and the frameworks never distinguish them. At Muntin the split is 0 agent-plane / 22 artifact-plane, and the conflation would have produced the exactly-wrong recommendation: orchestrate agents, from a correct diagnosis that says fix the build DAG.**
  - Gap: The source material was written from serving-a-product experience, where the agent graph IS the system. In a company whose product is a static site plus a data pipeline, the agent graph and the artifact graph are different objects with opposite prescriptions, and "19% of failures are graph-layer" is unreadable until you say which graph.
- **The NONE bucket is the finding, and no layer framework has a name for it. 46 of 118 (39%) are owned by no architectural layer — they require a price, a lawyer, a retraction, a feature, or the founder using his own product. That caps what any operating system can do at 61% of the backlog, and the residual is not noise: building architecture against it is precisely how 90 gates became 320 while 72 falsehoods stayed live. The structural response is a decision queue that agents may append to and may never close, hard-capped at 12.**
  - Gap: Every framework here implicitly promises that better architecture converts findings into fixes. None of them measures the fraction of findings architecture cannot touch, or says what to do with it. Without that number, a company reads a 26% close rate as an architecture failure and builds more architecture.
- **Absence-fragility as a first-class harness property: **an alarm's own liveness must be observable from outside the system it monitors.** Every Muntin alarm is downstream of activity — check-all runs on push, the heartbeat is a public-repo cron GitHub disables after 60 days of inactivity, and the crons that would fill the work queue die before their issue step. The correct instrument is one external notification whose *non-arrival* is the signal.**
  - Gap: The loop pattern (trigger, goal, state, evidence, feedback, stopping rule) assumes the loop runs and gives no way to detect that it stopped. For a one-person company whose defining risk is a quiet month, that is the single most consequential omission in the source material — and Muntin has already built the flawed version: a workflow authored specifically as the absence alarm, with one run in its history, that reported green while three published cadences were overdue.

## Rejected
- Building an agent orchestration graph — nodes, conditional edges, parallelism, joins, recovery. Zero of 118 findings are agent-plane flow failures. Muntin already ran the experiment (38 agents, ~5.8M tokens, 235 findings, 26% absorption); more routing multiplies input to a saturated queue and hands a one-person company a distributed-systems problem it did not have.
- The maker/reviewer write-permission split as a general architecture. Keep exactly one instance (protected paths), drop the rest. 80–84% of commits are already agent-authored with the founder as the only reviewer; a reviewer agent adds token cost and produces another report to a company measured at 26% report-absorption. Split by blast radius instead of by role.
- LLM-as-judge eval engineering — different model family, judge blind to the maker's reasoning, pinned and logged judge version, quality-vs-faithfulness scoring. Built for a served product with traffic to mine. Muntin has zero confirmed users, and the founder has never run the product end-to-end; building an eval harness before the first real trace exists is the same error as the 320 gates, one layer up.
- The full five-stage memory stack (capture, consolidate, retrieve, reconcile, decay). Adopt exactly one stage — decay — and skip the other four. The problem is volume, not retrieval: 178 docs / 34,058 lines, a 1,488-line board, and 307,721 lines of generated JSON added today. Explicitly reject "consolidate": this company's proven failure mode is producing a new summarizing document, and it has now done it five times.
- "Cost per accepted change" as the operating metric. It requires a rejection signal that does not exist here — PR #536 was merged with three reds accepted. The metric would read ~100% acceptance and tell the founder nothing. Use close-rate-of-prior-findings, which is real, already measured at 26%, and becomes free to recompute once commit trailers carry finding IDs.
- The Karpathy wiki pattern — compile the raw documents into a queryable wiki. Tempting against 178 docs, and wrong here: the company has already compiled four times (four 2026-07-28 syntheses, the strategic board, this audit) and every compilation became a new raw document nobody queried. Compilation without deletion is accumulation. Delete first; compile only what survives.
- The "verify CLAUDE.md adherence by having a second session review the transcript rule-by-rule" ritual, as a recurring practice. Worth doing once, when the files are next pruned. As a standing job it competes with the three that pay — and the specific failure it catches (a rule silently ignored) is cheaper to prevent by getting both CLAUDE.md files under 200 lines and moving situational guidance behind imports.
