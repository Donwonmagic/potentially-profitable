# Gate Epistemics — proving a gate can actually fail

## Thesis
I built the mutation harness and ran it, and the result is worse than the audit's hand count: of six gates tested with paired mutants, three are HOLLOW (they die when you corrupt the bytes they read but survive when you make the fact they protect false), and two more turned out to have no observation channel at all. A separate zero-registry experiment — running all 168 gates under a clock shifted forward 400 days — found that only 2 of 128 storefront gates and 1 of 40 product gates change their verdict when the entire published corpus becomes a year stale; at +4000 days it is still 2 of 128. The most important thing I learned was an accident: on my first run, three of six mutants silently failed to apply, and an unapplied mutant is indistinguishable from a hollow gate, so my harness reported "BROKEN" for gates that were fine. A gate-mutation harness without a positive control is itself epistemically hollow — the same disease it diagnoses — and no source you gave me addresses instrument-hollowness. So the deliverable is not "add mutation testing"; it is a three-layer instrument (paired artifact/truth mutants, an applied-assertion that makes a no-op mutant a loud invalid experiment, and a corpus-wide differential that needs no per-gate registry). On retirement, my honest assessment is that a CI check failing on obligation growth would not work and you should not build it: red is a currency this founder has already devalued (I reproduced the phantom rate — 7 idem reds locally today, 3 of which the deploy heals, 43%), and spending more red on hygiene spends a debased currency. Retirement must be a silent automatic demotion out of check-all with renewal earned by evidence a machine produces — a gate renews when its mutant kills it — not a new red for an exhausted human to triage. Do this in the order given: the phantom classifier first, because until red means something the founder cannot act on anything else you build.

## Design
### 1. `scripts/check-local.mjs` — the phantom classifier. BUILD THIS FIRST. [1 agent session (~2h). Founder review: 15 min, then use it daily instead of check-all.]
A wrapper the founder runs instead of check-all. It parses `wrangler.jsonc` `build.command` for the builders the deploy runs, parses check-all's `(idem)` entries, runs the suite, and prints failures in three labelled sections: BLOCKING (the deploy cannot heal this — the site stays down until you act), PHANTOM (the deploy runs this builder before checking; ignore, or run `--heal` to clear it locally), and UNKNOWN (not an idem entry — read it). Add `--heal`, which runs exactly the deploy-run builders and re-checks. Today it prints 4 BLOCKING and 3 PHANTOM. Computation prototyped at scratchpad/gm/phantom.mjs.

- Naive: The source material's answer is 'don't loop on confidence, loop on evidence' and the audit's answer is 'move the 56 tautologies to a pre-merge job.' Both treat the noise as a composition problem to be fixed by restructuring check-all.
- Evolved: Restructuring check-all is a multi-hour change to the file that gates the deploy, and if it goes wrong the site cannot ship. The founder needs red to mean something *this week*, before anything else on this list is worth building, because every other component reports its findings through the same channel. Classification is a 60-line read-only wrapper that touches nothing in the enforcing path and can be trusted on day one. Restructure check-all later, from a position where the founder already trusts the labels. Sequence matters more than elegance here: this is the only component that makes the other five legible.

### 2. `scripts/gate-mutants.mjs` + `gates/mutants/<gate>.mjs` — the paired-mutant harness. PROTOTYPE BUILT AND RUN. [Prototype exists. 1 agent session (~3h) to move it into the repo with the applied-assertion, plus ~30 min per new gate mutant thereafter. Founder review: 20 min to read the first verdict table.]
Working prototype at /tmp/claude-0/-home-user/21cedc96-0021-51e0-8cd2-ea41c98e3d82/scratchpad/gm/mutate-gates.mjs. Each registered gate declares two mutants: ARTIFACT (corrupt the literal bytes it reads) and TRUTH (make the world-fact it claims to protect false while leaving the artifact's shape valid). A transaction object records originals — file writes and directory moves — and restores in `finally`. Verdict matrix: artifact-killed + truth-killed = GROUNDED; artifact-killed + truth-survived = HOLLOW; both survived = BROKEN. Ship it as a `workflow_dispatch` job plus a nightly that opens one Issue per newly-HOLLOW gate. Results on the first 6 gates: HOLLOW × 4 (check-idem-coverage, check-security-claims, check-tool-verified-stamp, check-fabrications), plus check-counts-coherence and check-staleness-honesty which survived even their artifact mutants.

- Naive: Point mutmut-style mutation testing at the gate scripts — mutate the gate's own source and assert its test suite notices. That is what 'we already run mutmut-nightly for code' suggests doing.
- Evolved: Mutating a gate's source tests whether the gate has tests, and these gates have almost none — you would measure the wrong subject and get a uniformly damning, unactionable result. The failure mode here is not that gates are buggy; it is that gates are correctly implemented against the wrong subject. So the mutation must be applied to the SUBJECT, not the script. And the artifact/truth pairing is the load-bearing invention: a single mutant class cannot distinguish 'this gate is hollow' from 'this gate is broken', and those need opposite responses — a hollow gate needs a new assertion, a broken one needs deleting.

### 3. The applied-assertion — MUTANT-NOOP as a first-class verdict. THIS IS THE PART THAT MAKES THE INSTRUMENT HONEST. [Included in component 2's session. Founder review: none — but the rule belongs in CLAUDE.md in one line.]
The transaction object counts files whose content actually changed. If a mutant's apply function changes zero files, the harness reports MUTANT-NOOP (invalid experiment) and never scores the gate. Every result line prints the file count: `artifact=1(1f) truth=0(7f)`. Extend it with a per-mutant `expect` (minimum files, or a required post-condition string) so a mutant that applies to 1 file when it meant to apply to 40 is also caught.

- Naive: Nothing in the source material covers this. Standard mutation testing assumes mutants are compiler-validated source edits; the literature's failure mode is 'equivalent mutant', not 'mutant that never landed'.
- Evolved: On my first run, 3 of 6 mutants silently failed — a sentinel that wasn't on the page I chose, a JSON key formatted `"confidence": "x"` where my regex expected `"confidence":"x"`, and a fabrication phrasing the blocklist doesn't carry — and the harness confidently reported BROKEN for three gates, two of which were fine. Muntin's mutants must edit heterogeneous artifacts (HTML with inline CSS, YAML with meaningful comments, JSON, whole directories), which makes silent no-ops the normal case rather than the exception. Without the positive control, a gate-mutation harness reproduces exactly the disease it was built to diagnose: a check that reports a verdict it did not earn. IMPORTANT: do not ship component 2 without this.

### 4. `scripts/gate-differential.mjs` — corpus-wide environment perturbation, no per-gate registry. BUILT AND RUN. [Prototype exists and has run on both repos. 1 agent session (~2h) to add the other three axes and land it. Founder review: 10 min per quarterly matrix.]
Prototype at scratchpad/gm/clock-sweep.mjs + fake-clock.cjs. Runs every check-*.mjs twice — baseline and under a perturbed environment — and diffs the verdict vectors. The clock axis is a `node -r` preload that shifts `Date.now()` and bare `new Date()`. Add three more axes at near-zero marginal cost: NETWORK (a preload that throws on `fetch` — proves how many gates could ever consult the world, and is the honest measurement behind 'zero of 129 do network I/O'), READONLY (chmod the data dir; catches builders that write under a check flag), and CORPUS-SHRINK (hide 10% of content directories; any gate claiming coverage should notice). Publish the verdict-change matrix as `data/gate-epistemics.json`.

- Naive: Hand-classify all 320 checks as SHAPE or GROUNDING, as the audit did for 40. Or write a static classifier that greps each gate's source for `Date.now()`, `fetch(`, `existsSync`.
- Evolved: I built the static classifier too (scratchpad/gm/classify.mjs — 168 gates into 5 buckets: 7 execute/fetch, 10 clock, 52 enumerate+resolve, 58 partial-fs, 41 pure-text) and then measured it against the dynamic result. It is wrong in both directions. Ten gates statically touch the clock; only 3 change verdict under a 400-day shift — a ~73% false-positive rate, because reading the clock and being able to fail on it are different things. It also false-positives on `check-tool-no-fetch.mjs` and `check-sheet-no-fetch.mjs`, which match `/fetch\(/` because they *grep for that literal string* (stripping string and regex literals before scanning cut bucket A from 9 to 7 but does not fix the class). The differential has no such problem: it does not ask what a gate mentions, it asks what a gate does when the world changes. And it costs one script for the entire corpus, where mutants cost one registry entry each — which is what makes it affordable for a one-person company.

### 5. `docs/protected-truths.md` + `check-truth-coverage.mjs` — index by fact, not by gate. [1 agent session to widen both meta-gate root lists (~3h, expect 5-20 new entries to triage). Then 1 session to draft the registry from the mutant results (~2h). Founder review: 45 min — the registry is a founder judgement, not an agent one.]
A registry of the world-facts this company promises, each with an owner, a blast radius, and the gate + mutant that proves it. Seed it from what the mutants already exposed: every published number traces to live data (currently 0 gates); the counts on 951 pages are the site's real counts (0 gates — component 6 below); the tool logic was reviewed recently (0 gates — check-tool-verified-stamp proves only parseability); the security page states what security-claims.json states (0 gates — the count matcher survives total rewriting); the product CTA hostname resolves (0 gates). Coverage is reported as facts-with-a-killing-mutant over facts-registered. `check-truth-coverage.mjs` fails only when a registered fact's gate is HOLLOW or absent for more than one quarter.

- Naive: Keep the gate-coverage meta-gate (every check-*.mjs is wired or registered as UNWIRED) and widen its root list until it sees everything.
- Evolved: Widening the root list is necessary — 38 builders with `--check` are invisible to both meta-gates, and one of them, build-site-counts.mjs, is red right now — but it is not sufficient, and it is the fourth recurrence of the same fix. Every meta-gate here indexes by ARTIFACT (scripts on disk, entries in check-all), so its blind spot is always 'an artifact of a kind I did not enumerate'. Indexing by FACT has no such blind spot, because the enumeration is a human list of promises rather than a directory read. It also makes the count go the right way: today 168 gates cover perhaps a dozen distinct facts, and the registry makes that visible, which is the precondition for deleting gates without losing coverage.

Then register both mutants — artifact (corrupt a sentinel) and truth (delete 40 glossary directories, leaving manifest and sentinels untouched) — so the fix stays fixed.

- Evolved: The panel's brief says the last eval-engineering pass shipped 14 gate commits and changed nothing. The reason is that gate-quality work produces findings about gates, which is one abstraction level away from anything the founder can see. This component makes the very first output of the harness a visible, published falsehood being corrected — the Spanish footer of a company that sells honesty about numbers currently overstates its own tool count by 2.4x. Fix that in the same session that discovers it. Every closure in this company's history landed inside the session that found it; design for that fact rather than against it.

### 7. Expiry-by-default with mutation-earned renewal — the retirement mechanism, and NOT a CI check. [1 agent session (~3h) once components 2 and 3 are landed and ~20 gates have mutants. Founder review: 15 min/month on the digest.]
Every gate's header carries `@expires YYYY-MM-DD` (default: authored + 180 days). A nightly job moves expired gates from check-all's active array into a `QUARANTINE` array in the same file — they stop running, they are not deleted, and the move is a machine-authored commit. A gate is auto-renewed for another 180 days when its registered truth mutant kills it, i.e. when the machine has evidence it is load-bearing. A gate with no registered mutant cannot renew and always expires. The founder receives one monthly digest listing what quarantined and what renewed, with a one-command un-quarantine. Nothing about this ever turns CI red.

- Naive: The panel's own suggestion, and the natural read of the memory-engineering decay literature: a CI check that FAILS when the obligation count grows without a corresponding retirement.
- Evolved: I recommend against building that, and this is the honest assessment you asked for. Three reasons. First, currency: I measured 43% phantom reds on the founder's feedback channel today, so red is already devalued — adding a hygiene red spends money that has been inflated away, and a gate nobody heeds is exactly what this company already has 168 of. Second, Goodhart: a count budget is paid in the cheapest available coin, so a session that wants to add an expensive gate will retire a trivial one, and the count stays flat while the obligation load rises. Third, ownership: a growth gate makes retirement a founder decision requiring hours he does not have (53 obligation-hours/month against 13-26 available, ~10% actually paid). Expiry inverts all three — retirement is the default and costs zero founder-hours, renewal requires machine-produced evidence rather than an opinion, and the mechanism reports through a monthly digest rather than through the alarm channel. It also joins two things the source material keeps separate: mutation testing is the evidence, and memory decay is the policy, and neither of them alone can tell you which gate to keep. Caveat I will not hide: this only works once component 2 has mutants for a meaningful share of the corpus, because a gate with no mutant expires unconditionally. Set the initial expiry generously (12 months for existing gates, 180 days for new ones) so the mutant registry has time to catch up, and never let the quarantine job delete a file.

### 8. Two CLAUDE.md lines and one authoring rule — the cheapest component, and the one that stops the recurrence. [30 min in one session. Founder review: 5 min.]
Add to the storefront CLAUDE.md 'Key gates' section: (i) every new `check-*.mjs` header must declare the WORLD-FACT it grounds and its observation channel — a clock read, a resolution against disk, an execution, or a fetch — and a gate that only compares two committed artifacts must say 'X and Y agree' in its success line, never 'X is correct'; (ii) IMPORTANT: a gate and its truth mutant may not be authored in the same session. The second is enforced by convention plus a one-line check that a gate's mutant file has a different commit author-session than the gate.

- Naive: The software-factory pattern says split agents by WRITE PERMISSION so a reviewer that cannot edit what it reviews gives an honest report — which naively means standing up worktrees, a queue file, and a separate reviewer agent with restricted paths.
- Evolved: The worktree-and-queue machinery is real infrastructure for a team and pure overhead for one person whose agents already run sequentially; I am rejecting that part. But the principle underneath it transfers exactly, in miniature: a session that writes a gate will write a mutant that gate passes, because it is reasoning from the same model of the subject that produced the gate's blind spot. Separating the two authorings is the whole of the write-permission split as it applies here, and it costs one sentence. The declaration rule is the same economy — the company diagnosed this failure mode on 2026-07-30 and reproduced it inside the remediation seven days later, because nothing in the authoring process forces the distinction. Keep both under the 200-line CLAUDE.md budget by deleting the two `(idem)` paragraphs the phantom classifier makes obsolete.

## Advance
- **The paired artifact/truth mutant as an OPERATIONAL definition of a hollow gate. A gate is hollow iff it dies when you corrupt the bytes it reads and survives when you make the fact it claims to protect false. This converts 'is this gate shape or grounding?' from a reading exercise (the audit hand-classified 40 of 169 and stopped) into a two-line experiment with a verdict.**
  - Gap: Eval engineering builds judges for LLM output and has no vocabulary for a deterministic check that is correctly implemented against the wrong subject. Mutation testing mutates the code under test, which here would measure whether gates have unit tests — the wrong subject again. Nothing in the source material distinguishes a gate that is broken from one that is hollow, and those need opposite responses: hollow gets a new assertion, broken gets deleted.
- **Instrument-hollowness, and the applied-assertion that fixes it. A mutation harness must prove its mutant landed before it is allowed to score a survival, and report MUTANT-NOOP as an invalid experiment rather than as evidence about the gate. I hit this on 3 of 6 mutants in the first run and the harness confidently mislabelled two healthy gates as BROKEN.**
  - Gap: The mutation-testing literature assumes compiler-validated source mutants; its known failure mode is the equivalent mutant, not the unapplied one. When mutants are edits to heterogeneous artifacts — HTML with inline styles, YAML where comments carry meaning, JSON with variable whitespace, whole directories — silent no-ops are the normal case. Generalizes past Muntin: any harness that measures a system by perturbing it needs a positive control, and the eval-engineering material's insistence on grounding never turns that lens on the evaluator itself.
- **Differential environment perturbation as a zero-registry corpus classifier. Run the whole suite twice under a perturbed environment and diff the verdict vectors. The clock axis scored 168 gates with no per-gate work and produced a hard number: 2 of 128 storefront and 1 of 40 product gates can detect that the world moved a year. Extends to network, filesystem-permission, and corpus-shrink axes at near-zero marginal cost.**
  - Gap: The panel asked for a classifier so the corpus could be scored automatically 'rather than by hand', and the obvious answer — static analysis of gate source — I built and then measured as ~73% false-positive on its strongest signal. The advance is realising the classification question is dynamic, not static: not 'what does this gate mention' but 'what does this gate do when the world changes'. This is the affordability argument for a one-person company — mutants cost a registry entry each, perturbation axes cost one script for the whole corpus.
- **Mutation as the renewal criterion for a decay policy. A gate renews when its truth mutant kills it; a gate with no mutant, or whose mutant never kills, expires by default into quarantine. Retirement stops being a founder judgement and becomes an automatic consequence of machine-produced evidence.**
  - Gap: Memory engineering proposes decay for memory stores and offers dedup, consolidation, and recency as the criteria — all of which are proxies for value. None of them can tell you whether an obligation is load-bearing. Mutation testing can, and nobody joins the two. The join also answers 'never auto-merge contradictions, surface them': a gate that renews and a gate that expires are both machine decisions with an audit trail, but an un-quarantine is always the human's.
- **Decay must not be implemented as a red, because alarm-channel credibility is a measurable, spendable resource. I reproduced the phantom rate (7 idem reds locally, 3 healed by the deploy, 43%) and treat it as a currency problem: red is inflated here, so hygiene enforcement must be paid for in a different channel — a silent automatic demotion plus a monthly digest — while the alarm channel is reserved for facts that are actually false.**
  - Gap: Both the software-factory material ('a gate that fails closed') and the eval-engineering material ('any failure you do not turn into a permanent test, you will meet again') push everything toward CI-blocking enforcement, and neither prices what happens when the blocking channel's signal-to-noise falls below the point where the only human reads it. This is why the 2026-07-30 pass shipped 14 gate commits and moved nothing: it added enforcement to a channel that had already stopped being read. It also explains the sequencing in this design — component 1 exists solely to restore the currency before components 2 through 7 try to spend it.

## Rejected
- A CI check that FAILS when the obligation count grows without a retirement — the panel's own second candidate advance. Rejected, with the reasoning in component 7: red is 43% noise today so hygiene enforcement spends a debased currency; a count budget is Goodharted by retiring a trivial gate to buy an expensive one; and it makes retirement a founder decision costing hours against a 53-hours-due / 13-26-available budget. Expiry-by-default with machine-earned renewal delivers the same outcome with no red and no founder-hours. Build that instead.
- An LLM judge from a different model family, blinded to the maker's reasoning, with a pinned and logged version. Does not transfer. Gates are deterministic programs whose subject is on disk; a mutant is a cheaper, exactly reproducible, and strictly more trustworthy oracle than a judge, and a judge would introduce non-determinism and per-run cost into the one part of this system that currently has neither. Keep judges for prose grading where there is no ground truth.
- 'Measure the path, not just the answer' applied to gates. A deterministic gate has no path worth tracing — it reads files and compares. The whole informational content of a gate's behaviour is the verdict, and the only way to get information out of a verdict is to vary the input. Spending effort on gate tracing would be instrumentation of something already fully observed.
- 'Mine real traces rather than inventing tests.' Partially rejected on the facts here: gates almost never fail (312 of 320 pass), so there is no failure corpus to mine, and the reds that do exist are 43% phantom — mining them would teach the harness to model deploy-healing rather than defects. Mutants must be synthesized from the fact registry, not harvested. The principle holds where there IS a trace corpus, which in these repos means the four cron workflows already diffing and opening Issues that nobody works — a different panel's problem.
- The software factory's worktree-per-worker, queue file, and separate restricted-path reviewer agent. Overhead for one person whose agent sessions already run sequentially; the review bottleneck here is the founder's attention, which worktrees do not relieve. The underlying principle — an honest report requires that the reporter cannot edit its subject — is kept in miniature as the one-line rule that a gate and its truth mutant may not be authored in the same session (component 8).
- 'Cost per accepted change' and the 50% acceptance-rate floor as the governing metric. Needs a volume of independent changes with independent acceptance decisions that a one-person company reviewing its own agent output does not have; the denominator would be too small to be anything but noise, and optimising it would mean shipping smaller changes, which is the opposite of what a 26% close rate needs.
- Mutation coverage of all 168 gates as a goal. Each mutant is a real registry entry and real maintenance, and most of these gates protect facts nobody would be hurt by. Budget mutants to the protected-truths registry (component 5) and let everything else expire unrenewed — which is precisely the point of component 7.
- Repeating any statistic from the supplied source material — '19 of 20 PRs merge unreviewed', '97% error reduction', '83.9% quality vs 32.3% faithfulness', the '47x energy gap'. Every number in this design is one I measured in these repos with a command I can show. The mechanisms transferred; the numbers did not, and this company's own fact gate is the reason.
