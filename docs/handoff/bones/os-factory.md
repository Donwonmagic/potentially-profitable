# The Factory — queue, rooms, write-permission split, and the gate that lets him leave

## Thesis
Muntin does not need a factory built; it needs three specific wires connected, and two of them are one line each. The premise that the four diff-and-issue crons are "the cheapest unexploited mechanism" is wrong in a way that makes the fix cheaper, not harder: they are not unexploited, they are dead. `flake-tracker.yml` and `mutmut-nightly.yml` have failed 30 of their last 30 scheduled runs — I pulled the live log for run 31155758429 (2026-08-07 06:59:54Z) and it reads `HTTP 403: Resource not accessible by integration` on `gh run list --workflow=...`, because both workflows declare `contents: read` + `issues: write` and omit `actions: read`; and both repos have `totalCount: 0` issues, ever. The queue has produced zero items and 60+ red runs nobody reads. Second wire: the storefront has no pull-request CI at all — `check-all.mjs` (318 entries including the entire fact gate) is invoked only by `wrangler.jsonc` build.command step 76, `cost-index-refresh.yml` and `freshness-heartbeat.yml`; the three PR-triggered workflows are lighthouse, playwright and window-a11y. The honesty machine is on the wrong side of the merge button, which is the mechanism by which 72 falsehoods merged and stayed. Third: the 2026-07-30 eval pass shipped ~14 gates and zero prose corrections because gate-writing is the one kind of work an agent can finish inside its own session — so the write-permission split here must deny the Gatewright any write to `blog/`, `library/` or `data/`, cutting the escape hatch rather than the conflict of interest. Build the factory on primitives that already exist (`data/system-graph.json`, `scripts/rebuild-all.mjs`, the `since/who/drifts` registry shape at `check-idem-coverage.mjs:72`), keep concurrency at two storefront lanes because 47 of 397 scripts write into HTML trees and 1,248 of 1,368 pages share a CSS hash, and make closure machine-falsifiable — every queue item carries a `verify` command, and a gate re-runs it and reopens false closes. That last mechanism is the only thing in this design that directly attacks the 26%.

## Design
### C1 — Revive the producers, then gate workflow health from outside [20 min for the two permission lines; ~2 h for check-workflow-health.mjs plus its registry. One agent session total.]
Add `actions: read` to `permissions:` in `Muntin-Invoice-Decoder/.github/workflows/flake-tracker.yml:33` and `mutmut-nightly.yml:28`. Then write `scripts/check-workflow-health.mjs` (product repo, wired into `ci.yml` privacy-gates beside `check-gate-coverage`): it reads a declared registry `WORKFLOWS = { file: { cadenceHours, since, whoReads } }` and fails when any scheduled workflow has no `conclusion: success` within 2× its cadence. Registry entries mirror the `since/who/drifts` shape at `check-idem-coverage.mjs:72`. Also add a `--dry-run` path to both nightlies so the issue-opening step is exercised on `workflow_dispatch` without waiting a night.

- Naive: Point a scheduled agent session at the GitHub Issue queue the four crons produce.
- Evolved: There is no queue to point at. The crons produce zero issues and 60+ red runs; `list_issues` returns `totalCount: 0` for both repos in all states. A session pointed at that queue would find nothing, report green, and confirm the founder's belief that the machinery works. More importantly the company's own doctrine — `check-gate-coverage.mjs:15-19`, 'a gate nobody runs is not protection, it is the appearance of protection' — has no analogue for WORKFLOWS: `check-gate-coverage` only verifies a check script is REFERENCED in YAML, never that the workflow succeeded. That blind spot is exactly what let 30 consecutive nightly failures pass unnoticed. C1 fixes the instance and closes the class.

### C2 — The queue: one JSON file per item, claimed by git compare-and-swap, closed only by a re-runnable `verify` [1 agent session for queue.mjs + check-queue.mjs + schema; 1 more session to translate the audit's seven §2 items into seeded queue items with verifies.]
`queue/items/<YYYYMMDD>-<slug>.json` in each repo (product items stay in the private repo; storefront items are public, which costs nothing since the code and the falsehoods are already public). Schema: `{id, source: gate|cron|audit|founder, opened, priority, paths[], evidence: {file, line, command}, verify: {kind: 'command'|'attest', run, expect}, claim: {role, branch, at, expiresAt}, state, closedBy, closedAt, verifiedAt}`. Two scripts: `scripts/queue.mjs claim --role=<r>` (git pull --rebase → pick highest-priority unclaimed item whose `paths` fall inside the role's writable glob → write claim with `expiresAt = now+90m` → `git push`; a rejected push means someone else claimed it, so re-read and take the next) and `scripts/queue.mjs close --id=<id>` (runs `verify.run`, records exit code and output hash, refuses to close on non-zero). Gate `scripts/check-queue.mjs`, wired into check-all: re-runs `verify` for every item closed in the last 14 days and REOPENS any that fail; fails CI if any claim is expired-but-unreleased, or if a `kind: 'command'` item has no runnable command. Audit findings enter only through a translator session that supplies a `verify` per finding; findings that cannot be given one become `kind: 'attest'`, route to the founder lane, and are excluded from the close-rate denominator.

- Naive: A single queue file (JSONL), or GitHub Issues, with a `status: done` field an agent sets.
- Evolved: Three edits. (a) One file per item, not one file: two agents claiming DIFFERENT items touch different paths and never conflict; two claiming the SAME item conflict on one path and the loser's push is rejected — git's own ref compare-and-swap is the atomic claim, with no lock service and no daemon, and it works from the ephemeral container. (b) Not GitHub Issues as the record: both repos have zero issues ever, so there is no habit to extend; a check script cannot read Issues offline; and an Issue cannot carry a command a gate re-runs. Issues stay as the NOTIFICATION channel the crons already write to. (c) The `verify` field is the whole point. The measured close rate is 26% and every out-of-session closure was incidental — a `status` field is precisely the artifact that already failed eight times across 49 findings. Closure has to be falsifiable by a machine, and re-falsified on a clock, or 'done' stays a claim.

### C3 — `factory-gate`: the storefront pull-request gate that does not exist today [1 agent session for the workflow plus check-protected-paths.mjs. Hard prerequisite: the five out-of-chain builders must be run and committed first (~1 h, and `build-ingredient-state-record` needs the founder's Mac and API keys).]
New `.github/workflows/factory-gate.yml` on `pull_request`. Steps: (1) `node scripts/rebuild-all.mjs --pre-only` (the 21 out-of-chain builders, including the five blocking the deploy today); (2) `node scripts/rebuild-all.mjs --no-check` (the deploy's own order, read from `data/system-graph.json` so it cannot drift from `wrangler.jsonc`); (3) `git diff --exit-code` — a PR that leaves derived artifacts stale fails HERE, not in the deploy; (4) `node scripts/check-all.mjs`; (5) `node scripts/check-protected-paths.mjs`. Provenance: read `Co-Authored-By: Claude` from the PR's commit trailers → STRICT profile (steps 1–5 all blocking, plus `check-src-sentinel` once it exists); human-authored → steps 4–5 blocking, 1–3 advisory. Fail-closed: `rebuild-all` prints network/secret steps as SKIPPED; the gate FAILS if the PR touches any path a skipped step writes (read from the graph), so `skipped` can never read as `passed`. Protected paths (label `human-review-required`, merge blocked until a human review is recorded), derived from the audit: anything that publishes a NUMBER — `data/sourced-claims.json`, `claims.json`, `data/cost-index*.json`, `data/cost-lockfloat*`, `blog/cost-index-*/**`, and any diff hunk containing `<!-- src:`, `<!-- count:` or `<!-- repro:`; the pricing/billing spine — `apps/web/lib/pricing-constants.ts`, `apps/api/src/lib/stripe-tiers.ts`, `apps/api/src/routes/billing.ts`; the honesty contract — `methods/index.html`, `promises/**`, `receipts/**`, `llms.txt`, `scripts/no-llm-ci.sh`, `scripts/lib/fabrication-patterns.mjs`, `docs/warrant-canary.md`, `docs/transparency-*.md`; conventional — `.github/workflows/**`, `wrangler.jsonc`, `_redirects`, `_headers`, `apps/api/migrations/**`, `pnpm-lock.yaml`, `.env*`, `CODEOWNERS`, `CLAUDE.md`. Earned autonomy lives in `.factory/autonomy.json`: role → globs that may auto-merge, each with `since`, `widenedBy`, and `evidence` naming the ledger week that met the precondition (≥10 consecutive accepted changes in that glob, zero reverts, zero reopened verifies). No narrowing operation exists; to narrow, delete the file and re-earn.

- Naive: Add a gate that fails closed and lists protected paths.
- Evolved: The naive version is already here 318 times over and it does not help, because it runs after the merge. Moving `check-all` to the PR is the single highest-leverage change in this design, and it is blocked today for one reason: the gate is red on five builders nothing runs (`build-themes-review-board`, `build-theme-story-pages`, `build-cuisine-landing-pages`, `build-cost-index-picker`, `build-ingredient-state-record` — I verified all five appear 0 times in `wrangler.jsonc` and only the picker appears in any workflow). Steps 1–3 are what makes the wiring legal under CLAUDE.md's rule against wiring a failing gate: `rebuild-all --pre-only` clears them inside the gate itself. Second evolution: the protected-path list is not the conventional one. At a company whose differentiator is that it does not publish numbers it cannot stand behind, the protected surface is SENTINEL-SHAPED, not directory-shaped — a diff touching a line containing `<!-- src:` is more dangerous than a diff to a migration, and no path glob catches it. Third: autonomy widens only on a MEASURED precondition from C6, because an unconditional ratchet is the exact mechanism that took check-all from ~90 to 318 in 33 days.

### C4 — Write-permission split: six roles, one writable glob each, enforced by a hook and a gate [1 agent session for roles.json + check-role-scope.mjs + hooks; 30 min for the refresh-workflow staging fix; 30 min for CODEOWNERS.]
`.factory/roles.json` maps role → `writes` globs, and every worktree gets a `.factory/role` file at creation. `scripts/check-role-scope.mjs` (pre-push hook plus a factory-gate step) rejects any commit touching a path outside its role's glob. Roles: **Refresher** (bot) writes `data/**`, `cost-index/**`, `es/cost-index/**` only — it already exists as `cost-index-refresh.yml`; fix its staging to a path-scoped `git add -A` plus a denylist and delete the `git checkout -- .` at :313, which the graph shows discards four rebuilt artifacts. **Corrector** writes `blog/**`, `library/**`, `glossary/**`, `es/**` and NOTHING in `scripts/` or `data/` — this role has never existed and owns the 72 falsehoods. **Gatewright** writes `scripts/check-*.mjs`, `scripts/lib/**` and the registries, and NOTHING in `blog/`, `library/`, `data/`. **Builder** writes `apps/**`, `packages/**`, `services/**` in the product repo. **Reviewer** writes `queue/items/*.json` verdicts and nothing else — it physically cannot edit what it reviews. **Integrator** is the only role that may write `wrangler.jsonc`, `.github/workflows/**`, `_redirects`, `_headers`, `CLAUDE.md`, `.factory/**`, and the only one that runs `rebuild-all` and merges. Replace `.github/CODEOWNERS`'s single `* @donwonmagic` line with per-path owners so the protected set requests review mechanically.

- Naive: Split agents by write permission so a reviewer cannot edit what it reviews.
- Evolved: Reviewer-vs-author is the right idea aimed at the wrong pathology. Muntin's measured failure is not a reviewer laundering its own work; it is an agent REROUTING work it cannot finish into an artifact it can. Between 2026-07-28 and 07-30 the storefront gained 9 check scripts in three days while closing 0 of the 5 prose corrections those same audits called mandatory, and `scripts/lib/fabrication-patterns.mjs` has not been touched since 2026-07-05 despite four named fabrications ranked 'non-negotiable' on 07-11. So the cut runs between WORK TYPES: the Gatewright cannot write the number it found wrong, so its only legal output is a queue item with a `verify`; the Corrector cannot write a gate, so its only legal output is the corrected prose. The split converts 'I'll add a gate instead' from a temptation into a push rejection.

### C5 — Rooms: lanes derived from write surfaces, not from workers; one serialized integrator [~2 h for lanes.mjs plus the worktree bootstrap script. No new dependencies; `rebuild-all.mjs` and `system-graph.json` already exist as of commit 2c1b2a0d1.]
Worktrees named by LANE, not by task: `git worktree add ../mun-content` (Corrector), `../mun-gates` (Gatewright), `../mun-data` (Refresher). Product repo: one worktree per app package, effectively free. `scripts/lanes.mjs --check` reads `data/system-graph.json` and refuses to open a second worktree whose role's `writes` globs intersect an already-open lane's. Hard rule, encoded: **exactly one storefront content lane at a time**, because 47 scripts write `*/*/index.html` and 1,248 pages carry a CSS content hash. Data-lane and gates-lane may run concurrently with content. The JOIN is serialized and owned by the Integrator: `node scripts/rebuild-all.mjs` on an integration branch before any merge — never an ad-hoc order. Disk budget stated up front: each storefront worktree costs 1.2 GB of working tree (`.git` is shared), so three lanes is the practical ceiling; the product repo's 31 MB tree imposes no limit.

- Naive: One worktree per worker; run N agents in parallel.
- Evolved: Per-worker worktrees create N divergent derived-artifact states in a repo where the derived state IS most of the repo. Measured: three consecutive local `check-all` passes on the same tree gave 312 → 317 → 312 (`rebuild-all.mjs:9-13`) because clearing reds in an ad-hoc order does not converge — so two content workers do not merely conflict, they produce a tree no rebase reconciles and whose greenness depends on merge order. PR #534's own title records this having already happened: 'orphaned by a merge-order race'. The transferable half is isolation-by-write-surface plus a single integration order; the discardable half is one-room-per-worker.

### C6 — The ledger: cost per accepted change, computed from git, with a stop rule [1 agent session. Reads git and the queue directory; no new services, no network.]
`scripts/factory-ledger.mjs` emits `data/factory-ledger.json` weekly and on every factory-gate run: items minted / claimed / closed / **reopened by verify**; accepted-change rate = PRs merged and not reverted or `fix(`-patched within 14 days ÷ PRs opened; rework rate = share of commits whose subject starts `fix` touching a file another commit touched <14 days earlier (baseline 60/346 = 17.3% over 60 days); founder-review load proxy = count of `human-review-required` labels resolved; WIP age = max open-PR age (baseline 72 days, PR #374); headline **cost per accepted change = agent sessions started ÷ items closed AND still verifying at +14 days**. Stamp the baselines in the first run so the OS can be falsified: close rate 26%, in-session close rate 100%, median time-to-close 2 days, 42 merges / 60 days, 266 of 346 commits on 8 days. `scripts/check-factory-ledger.mjs` fails CI when the accepted-change rate is below 50% for two consecutive weeks, or when `reopenedByVerify` exceeds `closed` in any week.

- Naive: Track cost per accepted change; below 50% acceptance, stop — the loop is generating review work faster than it removes it.
- Evolved: The stop rule is right and I am adopting it, but 'acceptance' as the source material defines it (a human accepts the diff) is unmeasurable here — the founder merges nearly everything, 80–84% of commits are agent-authored, and the board records PR #536 merged with three reds he accepted. Acceptance-at-merge would read ~100% and prove nothing. The honest denominator is SURVIVAL: a change is accepted if it is still verifying 14 days later. That definition catches the exact recurring failure — `dea46ad34` regenerated the picker on 2026-07-28 and every bot read since has re-staled it, which scores as accepted at merge and rejected at +14d. Second evolution: publish `reopenedByVerify` beside `closed`, because a factory that closes fast and reopens faster is worse than one that closes slowly, and only the ratio tells you which one you have.

### C7 — Watchdog inversion: the private repo watches the public one, with a non-GitHub backstop [PAT plus workflow ~1 h; the Routine ~15 min; the header correction ~10 min.]
Move the outermost alarm out of the failure domain. (1) `Muntin-Invoice-Decoder/.github/workflows/storefront-watch.yml`, weekly: with a fine-grained PAT scoped to `actions: read` + `workflow: write` on `potentially-profitable`, assert `cost-index-refresh.yml` has a `success` within 7 days and `freshness-heartbeat.yml` within 9; on failure open/update a rolling issue AND `workflow_dispatch` the refresh. Private repos are not subject to the 60-day scheduled-workflow disable, so this alarm cannot be switched off by the silence it detects. (2) A CCR **Routine** on the founder's account (cron, fresh session per fire) that runs `queue.mjs claim --role=<r>` in the storefront and works one item — the only layer that survives GitHub disabling everything, because it is not GitHub. (3) Keep `freshness-heartbeat.yml` as the inner ring and demote it from outer ring in its own header comment: it has run exactly once ever and structurally cannot detect its own disablement. State plainly in the workflow header that whether bot pushes reset GitHub's 60-day activity clock is UNVERIFIED from this container — the design is built so the answer does not matter.

- Naive: Add a cron that alerts when the data goes stale.
- Evolved: That cron exists twice already (`freshness-heartbeat.yml`, `cost-index-snapshot-watch.yml`) and the pre-mortem named the trap: in a PUBLIC repo the alarm is disabled by exactly the inactivity it exists to detect. The evolution is not a better alarm but a better HOST — and Muntin has a free one, because the two repos differ in visibility (`potentially-profitable` `"private": false`; `Muntin-Invoice-Decoder` `"private": true`). The cross-repo PAT the board has listed as 'not minted' since 2026-07-30 pays for itself twice: it also automates the `vendor-cost-index.mjs` re-vendor that ADR-009 §7 has been calling a founder decision.

### C8 — The session contract: claim first, close last, WIP-limited [1 agent session for six role files plus the claim/close wiring. Depends on C2.]
`.factory/roles/<role>.md`, one short prompt file per role, loaded as the session's opening instruction. Contract: the session's FIRST tool call is `node scripts/queue.mjs claim --role=<r>`; if it returns nothing, the session ends and says so rather than inventing work. Its LAST call is `node scripts/queue.mjs close --id=<id>`, which runs the item's `verify` and refuses to close on a non-zero exit. Between them the session may only touch paths inside its role's globs (C4 enforces). `claim` refuses if the role already has an open PR older than 7 days — a hard WIP limit aimed directly at #374 (72d), #448 (55d), #534 (8d). Each role file names ONE handover artifact: the queue item's `closedBy` + `verifiedAt`, and nothing else — no board prose, no new document under `docs/`. A stale claim past `expiresAt` is reaped by the next `claim` call, so a session that dies mid-item does not park the work forever.

- Naive: Write a CLAUDE.md section telling sessions to work the backlog.
- Evolved: The company has already run that experiment at maximum strength and it produced nothing. The unfixed items carry the strongest labels available — 'not optional', 'non-negotiable', 'NEEDS THE FOUNDER, do not paper over', 'Do this Monday' — and 1 of 9 Rung-0 deliverables shipped in ten days. Prose in a file every session loads is exactly the artifact whose measured enforcement power is zero. Making the claim a TOOL CALL rather than an instruction converts backlog-working from something a session may do into the only way a session can legally begin, and the WIP limit converts 'don't leave PRs open' from an aspiration into a refusal. Honest limit: this constrains sessions started through the factory. An ad-hoc founder session still bypasses it — which is correct, and is why C3's protected paths, not C8, are what actually stop a bad change.

## Advance
- **Closure must be machine-falsifiable and re-falsified on a clock: every queue item carries a `verify` command, and a wired gate re-runs the verifies of recently-closed items and REOPENS the false ones. Items that cannot be given a runnable verify are typed `attest`, routed to the founder lane, and excluded from the close-rate denominator so the headline number stays honest.**
  - Gap: The software-factory material has a queue and a fail-closed gate but treats 'done' as a state an agent writes. Muntin has measured what that is worth: a 26% close rate across 49 findings, every out-of-session closure incidental, and `dea46ad34` re-staled by every bot run since. The source material never prices the FALSE CLOSE — and in a company where the only unit of work is an agent session that ends, the false close is the dominant failure, not the missed find.
- **Split agents by write permission so the cut runs between WORK TYPES, not between author and reviewer — the Gatewright may not write `blog/`, `library/` or `data/`, and the Corrector may not write `scripts/`. The split's job is to close the cheap-substitute escape hatch, not the conflict of interest.**
  - Gap: The source material models an agent tempted to approve its own work. Muntin's pathology is different and more interesting: an agent converts a finding it cannot close inside its session into an artifact it can — 9 new gates in 3 days against 0 of 5 mandated prose corrections, and 320 gates grown from ~90 in 33 days. A reviewer/author split does nothing about that; it is the same agent, honestly reporting, choosing a cheaper output. Nothing in the harness/loop/graph or factory material describes work-type substitution as a failure mode, let alone a permission boundary that prevents it.
- **An alarm must not share the outage mode of the thing it watches — and where a solo operator owns both a public and a private repo, the private one is the structurally correct host for the public one's watchdogs, because GitHub's 60-day scheduled-workflow disable applies only to public repos.**
  - Gap: Every source framework assumes the observability layer is available when you need it. The pre-mortem found the exact inversion here: the cron keeping the data alive is switched off by precisely the absence the alarms exist to detect, and `freshness-heartbeat.yml` — the absence alarm — lives inside the repo whose silence disables it and has run once ever. The transferable rule is 'observer outside the failure domain'; the Muntin-specific discovery is that the repos' visibility asymmetry hands him that observer for free, and that the same PAT also retires the cross-repo snapshot chore ADR-009 §7 has been calling a founder decision since 2026-07-28.
- **A gate whose greenness depends on execution order is a lottery, not a gate — so the factory's join step must execute the deploy's own order, READ from a derived graph rather than copied from it, and any gate promoted to pre-merge must first be reachable by that runner.**
  - Gap: 'Fail closed' presumes a determinism nobody checked. Here three consecutive `check-all` passes on the same tree gave 312 → 317 → 312, the only convergent order is an 84-step string inside `wrangler.jsonc` that runs solely in Cloudflare's container, and 37.5% of the reds a founder sees locally are phantoms the deploy heals. That converts a red gate into background noise — how PR #536 merged with three accepted reds. The fix is not a better gate; it is making the gate's input state reproducible (`system-graph.json` → `rebuild-all.mjs`, both of which landed 2026-08-07) and making the PR gate run that order before it judges.

## Rejected
- Do NOT build the multi-agent GRAPH layer (nodes, conditional edges, joins, recovery). The source material's own rule applies against it: never build the graph before you have watched real traces — and no queue-driven session has ever run here, so there are zero traces. The measured write-surface map caps useful storefront concurrency at one content lane plus one or two auxiliary lanes anyway (47 of 397 scripts write HTML trees; 1,248 of 1,368 pages share a CSS hash; each worktree costs 1.2 GB). An orchestration layer would be the 319th gate and the 17th planning document.
- Do NOT adopt the LLM-judge eval harness (different model family, judge blind to the maker's reasoning, pinned judge version). It spends tokens and founder-minutes on a gap Muntin does not have — the failure is not answer quality, it is that verdicts never reach an edge — and in the product repo it would put a language model inside the CI of a company whose strongest stranger-falsifiable differentiator is `scripts/no-llm-ci.sh` asserting that no language model reads your numbers. Judge the PATH with deterministic `verify` commands (C2) instead; that is the transferable half.
- Do NOT use GitHub Issues as the queue of record. Both repos have `totalCount: 0` issues across all states, so there is no habit to extend; a `check-*.mjs` cannot read Issues offline in the ephemeral container; and an Issue body cannot carry a command a gate re-runs. Keep Issues exactly where they already are — the crons' notification channel, once C1 revives them — and keep the record in files a gate can read and a diff can show.
- Do NOT stand up the five-stage memory system (capture / consolidate / retrieve / reconcile / decay) as new infrastructure. This company's memory is already 1,488 board lines plus a 993-line archive plus 16 planning documents at 2,723 lines, and its measured problem is that memory has no enforcement power — adding a better store repeats the 2026-07-30 mistake at higher cost. The only memory change the Factory needs is subtractive: the board's '⚠ OPEN — NEEDS THE FOUNDER' prose section becomes queue items with verifies, and the prose is deleted, not summarized.
- Do NOT adopt 'one worktree per worker' as written. In this repo the derived state IS most of the repo and the convergent order exists in one un-runnable string, so per-worker rooms produce N divergent trees whose greenness depends on merge order — PR #534's own title, 'orphaned by a merge-order race', records that having already happened. Take isolation-by-write-surface and a single serialized integrator; leave the per-worker room behind.
- Do NOT let 'earned autonomy only widens' stand unconditioned. A widening-only ratchet with no measured precondition is structurally identical to the mechanism that grew check-all from ~90 to 318 entries in 33 days and pushed obligations to 2.7x capacity. Keep the direction (widening only, never a silent narrowing) but require each widening to cite a specific ledger week that met a stated numeric precondition, and make re-earning — not quiet narrowing — the only way back.
