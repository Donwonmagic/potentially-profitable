# The Seam: what breaks between muntin.digital and Muntin Ledger, where neither repo's gates can see

## Thesis
Muntin is two repositories that behave like one company in exactly the places a content hash can check, and like two unrelated companies everywhere behavior crosses the seam. I enumerated 13 cross-repo invariants; 3 are enforced, and all 3 are byte-comparisons of vendored files (design tokens, mark geometry, data snapshots). Every invariant that concerns something *happening* — a hostname resolving, an enum matching, a price agreeing, a beacon landing in the same database — is enforced by nothing, and four of them are broken right now. The sharpest: `NEXT_PUBLIC_SITE_URL` is set in no wrangler config, no `.env`, no workflow, and no deploy script in either repo, so the product's build-inlined fallback `https://ledger.muntin.digital` ships as the canonical URL, sitemap host, robots sitemap pointer, `metadataBase` and Organization `@id` of an app whose only route is `app.muntin.digital/*` — while 396 indexable storefront pages (35.8% of the indexable site) send every product CTA to that same unrouted hostname. The repo's own `guard-web-deploy-env.mjs` blocks a deploy over exactly this failure mode for `NEXT_PUBLIC_API_BASE_URL` and never mentions its sibling. Meanwhile 100% of founding-list signups are silently relabeled `studio` — the retired web-studio line's name — because neither the storefront Worker's allowlist nor the product API's enum contains either value the live forms actually send. The good news is real and should be protected: the "two design languages" fork the founder-vision doc still describes as open is *closed* — the token spine is byte-identical and hash-locked on both sides — and both stale data snapshots re-vendored cleanly in this container with two commands.

## THE HOSTNAME — precisely what each repo configures, and what it does not
**Storefront exposure.** `grep -roh 'ledger\.muntin\.digital' --include="*.html"` → **547 occurrences across 405 files**. Of those 405, **396 are indexable** (I walked all 1,368 HTML files: 262 carry `noindex`, 1,106 are indexable) — so **35.8% of every indexable page on the site** carries a product CTA to this hostname. Also: 4 JSON-LD blocks embed it as a `url`/`@id`, `claims.json` and `data/sourced-claims.json` cite `https://ledger.muntin.digital/` as the *source of record* for the $19 founding claim, and it is hardcoded as a string literal in **15 distinct source files** — 5 page builders (`scripts/inject-ledger-cta.mjs:51`, `build-ingredient-yield-pages.mjs:773`, `build-cuisine-landing-pages.mjs:447`, `build-theme-story-pages.mjs:222`, `build-themes-review-board.mjs:297`), 5 tool JS/HTML files (`tools/vendor-benchmark/vendor-benchmark.js` ×3, `tools/_shared/cost-lockfloat-ui.js:603`, `tools/_shared/cost-index-ui.js`, `tools/plate-cost/index.html` ×2), 2 CSS files, and 2 data manifests. There is no single constant; repointing the host is a 15-file edit plus a rebuild. Occurrences of `app.muntin.digital` in the storefront: **zero**.

**What actually routes.** I read every routing config in both repos. `Muntin-Invoice-Decoder/apps/web/wrangler.jsonc:26-30` — routes `app.muntin.digital/*` on zone `muntin.digital`, and nothing else. `apps/api/wrangler.toml:21-23` — `api.muntin.digital/*`. `apps/email-worker/wrangler.toml:28` — "The Worker has no HTTP routes." `apps/web/next.config.ts` has `rewrites()` at line 197 and **no `redirects()`**. `infra/cloudflare/` contains exactly one file, `r2-lifecycle.json`. No Terraform, no `_redirects`, no `_routes.json`, no CNAME in the product repo. Storefront: `wrangler.jsonc` has no `routes` key at all (the keys are `$schema, name, compatibility_date, observability, main, build, assets, vars, durable_objects, migrations, kv_namespaces, ai, triggers`); `CNAME` = `muntin.digital`; `_redirects` is 259 lines with **zero** rules mentioning `ledger`. **`ledger.muntin.digital` is bound to nothing in version control, in either repo.**

**The second, independent defect.** `NEXT_PUBLIC_SITE_URL` appears in **10 product files** as `process.env.NEXT_PUBLIC_SITE_URL ?? "https://ledger.muntin.digital"` — `app/layout.tsx` (metadataBase + Organization/WebSite `@id` + OG image), `app/sitemap.ts:27`, `app/robots.ts:16`, `lib/canonical.ts:28`, `lib/seo-schema.ts:19`, `app/.well-known/security.txt/route.ts:14`, `app/page.tsx:23`, both `verify` pages, `MarketingBreadcrumb.tsx:29`. I searched every `.json`, `.jsonc`, `.toml`, `.yml`, `.sh`, `.mjs` and `.env` in the repo: **the variable is set nowhere.** It is a `NEXT_PUBLIC_*` value, so it is build-inlined — a runtime `vars` entry would have no effect, a distinction `apps/web/wrangler.jsonc` spends 12 comment lines explaining for `NEXT_PUBLIC_API_BASE_URL`. So the app deployed at `app.muntin.digital` declares its canonical URLs, its sitemap entries, its `robots.txt` sitemap pointer and its Organization identity at `ledger.muntin.digital`. `scripts/guard-web-deploy-env.mjs` exists specifically to abort a deploy when a build-inlined URL var is missing — it covers `NEXT_PUBLIC_API_BASE_URL` only, and its own header calls the failure mode "a sev."

**The repos disagree with themselves.** `runbooks/web-deploy.md:24` step 1 configures DNS for `app.muntin.digital`. `runbooks/well-known.md:22,51,55,84-86` verifies four production endpoints against `https://ledger.muntin.digital/...` and says "Do NOT copy the sister site's." `runbooks/founder-todos.md:58` **F18 is an OPEN todo**: "`.well-known/security.txt` reachable at production root — `curl -i https://ledger.muntin.digital/.well-known/security.txt`." That is the closest thing in either repo to an admission that this hostname's reachability has never been confirmed. `runbooks/launch-plan-2026-11-13.md:25` locks the topology: "`muntin.digital` = SEO + free tools + content; `ledger.muntin.digital` = conversion."

**Live DNS cannot be checked from this container** (no outbound to arbitrary hosts, no resolver). Two facts bound the answer, though. First: the storefront's own production hostname is *also* absent from version control (no `routes` key; bound via CNAME + a dashboard custom domain), so "hostnames live in the dashboard" is plausibly the founder's working model and `ledger.` may well be configured there. Second, and this is the part that matters either way: **wrangler treats `routes` declaratively.** A route present in the dashboard but absent from `apps/web/wrangler.jsonc` is removed by the next `pnpm --filter @muntin/web deploy:cf`. So even the optimistic case is a time bomb wired to the next web deploy.

## THE CURLS — exactly what to run and what each outcome means
Three commands, under a minute, and they settle the single largest open question in this audit.

```
curl -sS -o /dev/null -w '%{http_code} %{redirect_url}\n' https://ledger.muntin.digital/
curl -sSI https://app.muntin.digital/ | head -3
curl -s https://app.muntin.digital/robots.txt; curl -s https://app.muntin.digital/sitemap.xml | head -5
```

**Command 1 — the funnel question.**
- `200` → the route is configured in the Cloudflare dashboard, outside version control. Every CTA works today. The exposure becomes config drift: add `{"pattern":"ledger.muntin.digital/*","zone_name":"muntin.digital"}` to `apps/web/wrangler.jsonc` *before the next deploy*, or wrangler strips it. In this branch the `NEXT_PUBLIC_SITE_URL` fallback happens to be correct, which is luck, not design.
- `301`/`302` → a Cloudflare Redirect Rule exists. Every one of the 547 links takes a hop, and canonicals now point at a redirector — worth fixing, not an emergency.
- `530` or `1016` (Cloudflare origin/DNS error), or a resolver `NXDOMAIN` → **the hostname does not resolve.** Every product CTA on 396 indexable pages is dead, the two registered `source_url`s in `claims.json` point at nothing, and the 4 JSON-LD `url` fields are invalid. No gate in either repo would ever notice.
- `404` served with the storefront's chrome → the zone's catch-all is answering; functionally identical to dead.

**Command 2** — is the product deployed at all? A non-200 means the whole conversion surface is theoretical regardless of hostname.

**Command 3** — the `NEXT_PUBLIC_SITE_URL` question, settled empirically. If `robots.txt` says `Sitemap: https://ledger.muntin.digital/sitemap.xml` and `sitemap.xml` emits `ledger.` URLs while you fetched them from `app.`, the fallback is live in production and Google is being told the app lives somewhere it may not.

## THE LIVE SEAM BUG — every founding signup is stamped with the retired product line's name
This is the one I would fix today, because it is destroying the only measurable asset ADR-020's strategy depends on, it is silent, and it takes fifteen minutes.

**Layer 1 — what the live forms send.** `grep -roh 'name="source"[^>]*value="[^"]*"'` across all HTML gives, for the founding forms: `home-founding` at `index.html:828` and `es/index.html:835`; `ledger-pricing` at `ledger/index.html:673` and `es/ledger/index.html:615`. (The 613 `footer` and 162 `cost-index-ingredient` values belong to the newsletter form, a different handler.)

**Layer 2 — the storefront Worker.** `src/worker.js:8921`: `const WAITLIST_SOURCES = new Set(['studio', 'studio-hero', 'studio-product', 'studio-banner'])`. Line 8943: `const source = WAITLIST_SOURCES.has(body.source) ? body.source : 'studio';`

**Layer 3 — the product API.** `apps/api/src/routes/waitlist.ts:46` `ALLOWED_SOURCES = new Set(["hero", "waitlist_page", "demo", "studio", "studio-hero", …])`; line 111 coerces anything else to `"unknown"`.

**Neither allowlist contains either value the live forms actually send.** So 100% of founding-list signups arrive in the product database, and in the `funnel.waitlist_submitted` event, tagged **`studio`** — the name of the web-studio services line that was retired. The two real capture surfaces, the homepage founding band and the `/ledger/` pricing block, are permanently indistinguishable in the data, and every signup is attributed to a business the company no longer runs. Three layers, each internally consistent and each documented with a thoughtful comment (the product's enum even carries an eight-line explanation of the "pre-launch studio bridge"), and **zero reconciliation between them**. No gate on either side compares the values the HTML emits to the Worker's allowlist to the API's enum.

The capture itself works — it is first-party, forwarded server-to-server to `https://api.muntin.digital/v1/waitlist` with honeypot, timestamp, threat-IP and Turnstile layers. Only the label is wrong. That is the seam signature exactly: each side is well-built; the joint is unowned.

## THE MINIMUM VIABLE SEAM GATE — one file, no PAT, no network
The founder's real constraint is hours, so this has to be one script in the repo whose CI already runs 320 gates, using the pattern he already trusts: a **declared registry with dated reasons**, exactly like `check-gate-coverage.mjs`'s `UNWIRED` and `check-idem-coverage.mjs`'s `MANUAL`.

**`potentially-profitable/scripts/check-product-seam.mjs`**, wired into `check-all.mjs`, reading one new committed contract file `data/product-seam.json`. Four assertions:

1. **Host binding.** Walk every HTML file (declared roots + explicit skip list, per the repo's own rule). Collect every external `https://<host>/` whose host ends in `muntin.digital`. Each must appear in `product-seam.json.hosts[]` with a `routedBy` field naming the repo + file that binds it (`"Muntin-Invoice-Decoder/apps/web/wrangler.jsonc routes[]"`). Today `ledger.muntin.digital` has no binder → **fail**, and it stays failing until either the route literally lands in that file or the CTAs are repointed at `app.muntin.digital`. This does not resolve DNS; it asserts that somebody wrote down where the hostname comes from — which is the whole failure.
